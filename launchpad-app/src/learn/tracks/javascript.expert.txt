=== js4-01 | Proxy and Reflect: objects with rules
--- teach
The advanced course showed how JavaScript works underneath. This course builds the machinery other code stands on — proxies, emitters, middleware, pools, stores, a parser and a test runner — and hunts the performance and timing bugs that only show up under load or bad timing.

A **Proxy** wraps an object and lets you intercept the basic operations on it — reading a property, writing one, deleting one, listing keys. You supply a **handler** whose methods (called **traps**) run instead of the default behaviour:

```js
const loud = new Proxy({ name: 'ada' }, {
  get(target, key, receiver) {
    const value = Reflect.get(target, key, receiver)
    return typeof value === 'string' ? value.toUpperCase() : value
  },
})
loud.name     // 'ADA'
```

**Reflect** has one function for every trap (`Reflect.get`, `Reflect.set`, `Reflect.deleteProperty`, `Reflect.has`, …) that performs the *default* operation. Inside a trap, do your extra work and then hand over to `Reflect` for the normal behaviour, passing along every argument you received — especially `receiver`, which keeps getters and inheritance working.

The traps you will use most:

- `set(target, key, value, receiver)` — must **return `true`** when the write succeeded. Returning `false` (or nothing, which is `undefined`) makes the assignment throw a `TypeError` in strict mode. `return Reflect.set(…)` gets this right for free.
- `deleteProperty(target, key)` — likewise returns a boolean.
- `get(target, key, receiver)` — returns the value to use.

Proxies are how libraries give plain-looking objects superpowers: Vue's reactivity, validation layers, change tracking, default values, read-only views. Two patterns cover most uses:

- **Validation** — the `set` trap checks the key and value, and throws before anything is stored, so an invalid state can never exist.
- **Observation** — the `set` and `deleteProperty` traps perform the change, then tell someone about it.

Mistakes to avoid: writing to `receiver` (the proxy) inside a `set` trap — `receiver[key] = value` calls the trap again, forever; forgetting to return `true`; and firing change notifications when the value did not actually change, which makes listeners do pointless work. Compare with `Object.is(old, value)`, which is `===` except that `NaN` equals `NaN` (and `0` and `-0` differ). A related helper you will want: `Object.hasOwn(obj, key)` is true when `obj` itself has `key`, not something it inherits.
--- task
Write:

- `validated(schema)` — `schema` maps field names to predicate functions. Return a proxy over a new empty object where setting a field that is not in the schema throws `new TypeError('unknown field: <key>')`, setting a value the field's predicate rejects throws `new TypeError('invalid value for <key>')`, and anything else is stored normally.
- `observable(target, onChange)` — return a proxy over `target`. After a property is set to a value that is different (by `Object.is`) from its current value, call `onChange(key, oldValue, newValue)`. Setting the same value calls nothing. Deleting a property that exists calls `onChange(key, oldValue, undefined)`. Writes go through to `target`.

--- solution
function validated(schema) {
  return new Proxy({}, {
    set(target, key, value, receiver) {
      if (!Object.hasOwn(schema, key)) throw new TypeError(`unknown field: ${String(key)}`)
      if (!schema[key](value)) throw new TypeError(`invalid value for ${String(key)}`)
      return Reflect.set(target, key, value, receiver)
    },
  })
}

function observable(target, onChange) {
  return new Proxy(target, {
    set(obj, key, value, receiver) {
      const old = obj[key]
      const ok = Reflect.set(obj, key, value, receiver)
      if (ok && !Object.is(old, value)) onChange(key, old, value)
      return ok
    },
    deleteProperty(obj, key) {
      const had = Object.hasOwn(obj, key)
      const old = obj[key]
      const ok = Reflect.deleteProperty(obj, key)
      if (ok && had) onChange(key, old, undefined)
      return ok
    },
  })
}
--- hint
Both are `new Proxy(target, { set(…) { … } })`. Finish every `set` trap with `return Reflect.set(target, key, value, receiver)`.
--- hint
In `validated`, check `Object.hasOwn(schema, key)` first, then `schema[key](value)`, and throw before storing anything.
--- hint
In `observable`, read the old value before the write, and call `onChange` only if `!Object.is(old, value)`. Add a `deleteProperty` trap for deletes.

=== js4-02 | WeakMap: private data and caches that do not leak
--- teach
A `WeakMap` is a Map with three differences: its keys must be **objects**, you cannot list or count its entries, and it holds its keys **weakly** — if nothing else in the program refers to a key object any more, the garbage collector may remove the object and its entry together.

That makes it perfect for **attaching data to objects without touching them**:

```js
const visits = new WeakMap()
function visit(user) {
  visits.set(user, (visits.get(user) ?? 0) + 1)
  return visits.get(user)
}
const ada = { name: 'ada' }
visit(ada)
visit(ada)          // 2
Object.keys(ada)    // ['name'] — the count is not on the object at all
```

Two classic uses:

**Private data.** Before `#private` fields existed, libraries kept an object's secrets in a module-level WeakMap keyed by the object. Code outside the module has no way to reach the map, so the data is truly private, and when the object is dropped its secret goes with it. The technique still matters for objects you do not own — a DOM node, another library's instance — where you cannot add fields.

**Caches.** Caching a computed result per object in a normal `Map` keeps every object you ever cached alive for ever: a **memory leak**. Keyed weakly, the cache entry disappears when the object does.

Things that surprise people: `new WeakMap().set('text', 1)` throws, because a string is not an object; there is no `size`, no `keys()`, no iteration — by design, since entries can vanish at any moment; and a WeakMap does not make a *value* weak, only the key. If the value refers back to its own key, that is fine — the pair is collected together.
--- task
Write:

- a module-level `const balances = new WeakMap()` and a `class Account` that keeps each account's balance in it (not in a property or a `#` field). `new Account(owner)` sets `this.owner` and a balance of 0. `deposit(amount)` adds (a `RangeError` unless the amount is a positive number), `withdraw(amount)` subtracts (a `RangeError` if the amount is not positive or is more than the balance), and a `balance` getter reads it. There is no setter.
- `summary(obj)` — returns the object's own keys, sorted, joined with `','`. Cache the result per object in a WeakMap, and add 1 to the top-level `let computations` each time you actually compute one.

let computations = 0
const balances = new WeakMap()
const summaries = new WeakMap()

class Account {
  constructor(owner) {
    this.owner = owner
    balances.set(this, 0)
  }

  deposit(amount) {
    if (!(typeof amount === 'number' && amount > 0)) throw new RangeError('deposit must be positive')
    balances.set(this, balances.get(this) + amount)
  }

  withdraw(amount) {
    if (!(typeof amount === 'number' && amount > 0)) throw new RangeError('withdrawal must be positive')
    if (amount > balances.get(this)) throw new RangeError('insufficient funds')
    balances.set(this, balances.get(this) - amount)
  }

  get balance() {
    return balances.get(this)
  }
}

function summary(obj) {
  if (!summaries.has(obj)) {
    computations++
    summaries.set(obj, Object.keys(obj).sort().join(','))
  }
  return summaries.get(obj)
}
--- hint

--- hint

--- hint

=== js4-03 | An event emitter
--- teach
An **event emitter** lets one part of a program announce "this happened" without knowing who cares. Listeners subscribe to an event name; `emit` calls each of them with the event's data. Node's `EventEmitter`, the DOM's `addEventListener` and most UI frameworks are built on this pattern.

The core is a `Map` from event name to an array of listener functions:

```js
const listeners = new Map()
function on(event, fn) {
  if (!listeners.has(event)) listeners.set(event, [])
  listeners.get(event).push(fn)
}
function emit(event, ...args) {
  for (const fn of listeners.get(event) ?? []) fn(...args)
}
```

The details are where real emitters earn their keep:

- **Unsubscribing.** Returning an "off" function from `on` is the most convenient API: `const off = emitter.on('save', fn)` … `off()`. It closes over exactly the right event and function.
- **`once`.** Wrap the listener in a function that removes itself and then calls the original.
- **Changing the list during an emit.** A listener may unsubscribe itself (every `once` listener does!) or add another listener while `emit` is looping. Removing items from an array you are iterating over skips the next item. Iterate over a **copy** of the list taken when `emit` starts, so changes take effect from the next emit.
- **The `'error'` event.** Node's rule is worth copying: emitting `'error'` when nobody listens **throws** the error, rather than silently losing it.

A memory-leak warning comes with the pattern: every listener stays alive for as long as the emitter does, along with everything it closes over. Components that subscribe must unsubscribe when they are done.
--- task
Write `class Emitter` with:

- `on(event, fn)` — adds a listener and returns a function that removes it.
- `off(event, fn)` — removes one registration of `fn` (the same function may be registered more than once).
- `once(event, fn)` — a listener that runs at most once; also returns a remover.
- `emit(event, ...args)` — calls the event's listeners in the order they were added, using the list as it was when the emit started; returns how many listeners it called. If `event` is `'error'` and there are no listeners, throw `args[0]` instead.
- `listenerCount(event)` — how many listeners the event has.
--- starter
class Emitter {
  constructor() {
    this.listeners = {}
  }

  on(event, fn) {
    this.listeners[event] = fn
  }

  emit(event, ...args) {
    if (this.listeners[event]) this.listeners[event](...args)
  }
}
--- solution
class Emitter {
  #listeners = new Map()

  on(event, fn) {
    if (!this.#listeners.has(event)) this.#listeners.set(event, [])
    this.#listeners.get(event).push(fn)
    return () => this.off(event, fn)
  }

  off(event, fn) {
    const list = this.#listeners.get(event)
    if (!list) return
    const i = list.indexOf(fn)
    if (i >= 0) list.splice(i, 1)
  }

  once(event, fn) {
    const wrapper = (...args) => {
      this.off(event, wrapper)
      fn(...args)
    }
    return this.on(event, wrapper)
  }

  emit(event, ...args) {
    const list = [...(this.#listeners.get(event) ?? [])]
    if (event === 'error' && list.length === 0) throw args[0]
    for (const fn of list) fn(...args)
    return list.length
  }

  listenerCount(event) {
    return this.#listeners.get(event)?.length ?? 0
  }
}
--- hint
Store a `Map` from event name to an **array** of functions. `on` returns `() => this.off(event, fn)`.
--- hint
`once` registers a wrapper that calls `this.off(event, wrapper)` before calling `fn`.
--- hint
In `emit`, copy the list first (`[...list]`) and loop over the copy.

=== js4-04 | Design: a middleware pipeline
--- teach
Web servers, bots and build tools all face the same design problem: every request needs several independent steps — logging, error handling, authentication, routing — and one tangled function that does them all becomes impossible to change. The **middleware** pattern (Koa, Express, Redux) solves it.

Each middleware is a function `async (ctx, next)`. `ctx` is a shared context object for this request. `next()` runs **the rest of the pipeline** and returns a promise that settles when the rest is done. So a middleware can act before, after, or instead of everything that follows:

```js
async function timer(ctx, next) {
  const start = Date.now()
  await next()                           // everything downstream runs here
  ctx.ms = Date.now() - start            // then we are back, on the way out
}
async function guard(ctx, next) {
  if (!ctx.user) return (ctx.status = 401)   // short-circuit: never call next
  await next()
}
```

Picture an onion: the request passes inwards through each layer's "before" part, and the response passes back out through each "after" part in reverse order. An error thrown deep inside travels back out as a rejected `next()`, so an outer middleware can `try { await next() } catch …` and turn any failure into a clean response.

`compose(middlewares)` turns the list into a single function. The idea is a `dispatch(i)` that calls middleware `i`, passing a `next` of `() => dispatch(i + 1)`; past the end, `dispatch` does nothing. Two details make it robust:

- Always return a **promise** from `dispatch`, even when a middleware throws synchronously — wrap the call so the error becomes a rejection.
- Calling `next()` **twice** from one middleware would run everything downstream twice. Detect it and reject with an error.

The design win: each concern is a small function that can be tested alone, reordered, reused, or removed — and adding a new concern means adding one function, not editing a tangle.
--- task
First, write `compose(middlewares)`: it returns `(ctx) => Promise`. Middleware `i` is called with `(ctx, next)`, where `next()` calls middleware `i + 1` and returns a promise of its completion; calling `next` past the end resolves at once. If a middleware throws or rejects, the composed promise rejects with that error. If a middleware calls `next()` a second time, that call rejects with `new Error('next() called twice')`.

Then replace the tangled `app` with four middlewares and `const app = compose([logger, errors, auth, router])`:

- `logger` — after the rest has run, pushes `'<path> <status>'` onto `ctx.log`.
- `errors` — if the rest throws, sets `ctx.res = { status: 500, body: err.message }`.
- `auth` — without `ctx.req.token`, sets `ctx.res = { status: 401, body: 'unauthorized' }` and stops; otherwise continues.
- `router` — `/hello` gives `{ status: 200, body: 'hello <token>' }`, `/boom` throws `new Error('kaboom')`, anything else `{ status: 404, body: 'not found' }`.

--- solution
function compose(middlewares) {
  return (ctx) => {
    let last = -1
    function dispatch(i) {
      if (i <= last) return Promise.reject(new Error('next() called twice'))
      last = i
      const fn = middlewares[i]
      if (!fn) return Promise.resolve()
      try {
        return Promise.resolve(fn(ctx, () => dispatch(i + 1)))
      } catch (err) {
        return Promise.reject(err)
      }
    }
    return dispatch(0)
  }
}

async function logger(ctx, next) {
  await next()
  ctx.log.push(`${ctx.req.path} ${ctx.res.status}`)
}

async function errors(ctx, next) {
  try {
    await next()
  } catch (err) {
    ctx.res = { status: 500, body: err.message }
  }
}

async function auth(ctx, next) {
  if (!ctx.req.token) {
    ctx.res = { status: 401, body: 'unauthorized' }
    return
  }
  await next()
}

async function router(ctx) {
  const { path, token } = ctx.req
  if (path === '/hello') ctx.res = { status: 200, body: `hello ${token}` }
  else if (path === '/boom') throw new Error('kaboom')

}

=== js4-05 | A promise pool: concurrency with a limit
--- teach
`Promise.all(items.map(fetchOne))` starts **everything at once**. For five requests that is fine; for five thousand it floods the server, trips rate limits and runs out of sockets. What you want is a **pool**: at most `limit` jobs running at any moment, and as soon as one finishes, the next one starts.

The first thing to get right is that jobs must be **functions that start work**, not promises. A promise is work that has already started — by the time you have an array of promises, it is too late to limit anything. So a pool takes `tasks`, an array of `() => Promise`, and calls each one only when there is room.

The neatest design uses **workers**: start `limit` async loops, and let each one repeatedly take the next unclaimed task until none are left.

```js
let next = 0
async function worker() {
  while (next < tasks.length) {
    const i = next++            // claim a task (no await between check and claim)
    results[i] = await tasks[i]()
  }
}
```

Because JavaScript runs one thing at a time, `next++` can never be claimed by two workers at once — there is no `await` between reading `next` and incrementing it. Storing by index `i` keeps results in the **input order**, even though jobs finish in any order.

Then `await Promise.all(workers)` waits until every loop has run dry. Start `Math.min(limit, tasks.length)` workers so an empty task list resolves straight away.

What about failure? The simplest useful rule is Promise.all's: if a task rejects, the whole pool rejects with that error. (Production pools often offer an `allSettled` mode too.) The mistake to avoid is *pre-starting*: writing `tasks.map((t) => t())` anywhere — even "just to get the promises ready" — runs every job immediately and the limit means nothing.

If any task rejects, reject with its error. An empty array resolves to `[]`.

=== js4-06 | A tiny reactive store
--- teach
Redux, Zustand, Pinia and friends all share one small idea: keep the application's state in **one place**, change it only through **described actions**, and let anyone **subscribe** to hear about changes.

```js
function reducer(state, action) {
  if (action.type === 'add') return { ...state, count: state.count + action.by }
  return state
}
reducer({ count: 1 }, { type: 'add', by: 2 })   // { count: 3 }
```

A **reducer** is a pure function `(state, action) => newState`. It never edits the old state; it returns a new object for a change, and the **same object** when the action does not concern it. That rule is what makes change detection cheap: the store can tell whether anything changed with a single `===`, no deep comparison needed.

The store itself is a closure around the current state and a list of listeners:

- `getState()` returns the current state.
- `dispatch(action)` runs the reducer; if the result is a different object, it stores it and calls every listener.
- `subscribe(fn)` adds a listener and returns an unsubscribe function.

Real UIs add **selectors**: a component usually cares about a slice of the state (`state.user`), not all of it. `select(selector, fn)` remembers the selected value and calls `fn` only when *that* value changes — which works precisely because the reducer returns the same object for unchanged parts.

Mistakes to watch for: a reducer that mutates (`state.count++; return state`) — the store sees the same object and tells nobody; notifying when nothing changed, which re-renders everything on every action; and listeners that unsubscribe during a notification, which skip their neighbours if you loop over the live list. Loop over a copy.
--- task

- `reducer(state, action)` for state `{ count, user }`: `{ type: 'increment' }` returns a new state with `count + 1`; `{ type: 'rename', name }` returns a new state with `user` set to `name` — unless `user` is already `name`, in which case it returns the same state; any other action returns the same state.
- `createStore(reducer, initialState)` returning `{ getState, dispatch, subscribe, select }`:
  - `dispatch(action)` — computes the next state; only if it is a different object, stores it and calls every listener with the new state (looping over a copy of the listeners).
  - `subscribe(fn)` — returns an unsubscribe function.
  - `select(selector, fn)` — subscribes so that `fn(newValue, oldValue)` is called only when `selector(state)` changes (by `Object.is`); returns an unsubscribe function.

function createStore(reducer, initialState) {
  let state = initialState
  let listeners = []

  const subscribe = (fn) => {
    listeners.push(fn)
    return () => {
      listeners = listeners.filter((l) => l !== fn)
    }
  }

  return {
    getState: () => state,
    dispatch(action) {
      const next = reducer(state, action)
      if (next !== state) {
        state = next
        for (const fn of [...listeners]) fn(state)
      }
      return action
    },
    subscribe,
    select(selector, fn) {
      let current = selector(state)
      return subscribe((s) => {
        const value = selector(s)
        if (!Object.is(value, current)) {
          const old = current
          current = value
          fn(value, old)
        }
      })
    },
  }
}

=== js4-07 | Deep equality and deep cloning
--- teach
`===` on objects asks "is this the **same** object?", not "do these look the same?". Two separately built `{ a: 1 }` objects are not `===`. And spread copies only one level. Sooner or later you need both **deep equality** and **deep copies** — and writing them teaches you exactly how JavaScript values are shaped.

For copies, the platform has an answer: **`structuredClone(value)`** deep-copies objects, arrays, `Date`, `Map`, `Set`, typed arrays and even **cyclic** structures.

```js
const original = { when: new Date(0), tags: new Set(['a']), nested: { n: 1 } }
const copy = structuredClone(original)
copy.nested.n = 2
original.nested.n       // 1
copy.when instanceof Date   // true
```

Know its limits: functions cannot be cloned (it throws), class instances come back as plain objects (their methods are gone), and getters are run and replaced by their values. Use it in real code — but you should understand what it does, so here you write your own.

**Deep equality**, recursively:

1. Primitives are equal if `===` — except `NaN`, which should equal `NaN`.
2. Two `Date`s are equal if their times are equal.
3. An array only equals an array: same length, items deep-equal in order.
4. Plain objects: same number of own keys, and every key of one exists in the other with a deep-equal value. **Key order does not matter** — which is why comparing `JSON.stringify` output is wrong.

**Deep cloning**, recursively, with one subtlety: **cycles**. If an object contains itself (`o.self = o`), naive recursion never ends. The fix is a `Map` from each original object to its copy, filled in *before* recursing into its children. When you meet an object you have already started copying, return its copy from the map. The same map also preserves **shared references**: if two places point at one object, the clone has two places pointing at one copy.

function deepEqual(a, b) {
  if (a === b) return true
  if (Number.isNaN(a) && Number.isNaN(b)) return true
  if (typeof a !== 'object' || typeof b !== 'object' || a === null || b === null) return false
  if (a instanceof Date || b instanceof Date) return a instanceof Date && b instanceof Date && a.getTime() === b.getTime()
  if (Array.isArray(a) !== Array.isArray(b)) return false
  if (Array.isArray(a)) return a.length === b.length && a.every((x, i) => deepEqual(x, b[i]))
  const ka = Object.keys(a)
  const kb = Object.keys(b)
  return ka.length === kb.length && ka.every((k) => Object.hasOwn(b, k) && deepEqual(a[k], b[k]))
}

function deepClone(value, seen = new Map()) {
  if (typeof value !== 'object' || value === null) return value
  if (seen.has(value)) return seen.get(value)
  if (value instanceof Date) return new Date(value.getTime())
  if (value instanceof Map) {
    const copy = new Map()
    seen.set(value, copy)
    for (const [k, v] of value) copy.set(k, deepClone(v, seen))
    return copy
  }
  if (value instanceof Set) {
    const copy = new Set()
    seen.set(value, copy)
    for (const v of value) copy.add(deepClone(v, seen))
    return copy
  }
  const copy = Array.isArray(value) ? [] : {}
  seen.set(value, copy)
  for (const key of Object.keys(value)) copy[key] = deepClone(value[key], seen)
  return copy
}

=== js4-08 | Debugging: money, floating point and BigInt
--- teach
JavaScript numbers are 64-bit binary floating point. They store most decimal fractions **approximately**, because 0.1 has no exact binary form — just as 1/3 has no exact decimal form.

```js
0.1 + 0.2                  // 0.30000000000000004
1.15 * 1.1                 // prints 1.265, but the stored value is a hair below it
(1.15 * 1.1).toFixed(2)    // '1.26' — so a customer is short-changed a cent
Number.MAX_SAFE_INTEGER    // 9007199254740991
2 ** 53 + 1                // 9007199254740992 — whole numbers stop being exact too
```

`toFixed` does not save you: it rounds the approximate value, and when the true answer ends in exactly half a cent, the approximation may sit just below it and round the wrong way. Past about 15–16 significant digits, even whole numbers lose precision.

The fix every payments system uses: **never store money as fractional numbers**. Store an **integer number of the smallest unit** (cents), do all arithmetic on integers, and convert to text only for display. For amounts that may exceed `Number.MAX_SAFE_INTEGER` cents, use **BigInt** — whole numbers of any size, written with an `n` suffix:

```js
const cents = 123456789012345678n + 1n     // exact
cents / 100n                                 // 1234567890123456n — BigInt division drops the fraction
cents % 100n                                 // 79n
```

BigInt rules: you cannot mix it with ordinary numbers (`1n + 1` throws — convert with `BigInt(x)`), division truncates toward zero, and there are no decimals, so **you** decide how to round. "Round half up" for a non-negative amount is `(x + 50n) / 100n` when dividing by 100.

Parse money from **text**, not through `parseFloat`: split on the dot and build the cents from the digits. And when splitting a bill, integer division leaves a remainder that must go somewhere — give the leftover cents to the first people, so the parts always add back up to the total exactly.

The debugging lesson: when a sum is off by a cent, print the full value (`console.log(x)` rather than `x.toFixed(2)`) — the hidden `...9999999` tells you it is a representation problem, not a logic problem.

function toCents(text) {
  const m = /^(-)?(\d+)(?:\.(\d{1,2}))?$/.exec(text.trim())
  if (!m) throw new SyntaxError(`not an amount: ${text}`)
  const cents = BigInt(m[2]) * 100n + BigInt((m[3] ?? '').padEnd(2, '0'))
  return m[1] ? -cents : cents
}

function formatCents(cents) {
  const sign = cents < 0n ? '-' : ''
  const abs = cents < 0n ? -cents : cents
  return `${sign}${abs / 100n}.${String(abs % 100n).padStart(2, '0')}`
}

function total(prices) {
  return formatCents(prices.reduce((sum, p) => sum + toCents(p), 0n))

=== js4-09 | A tokenizer
--- teach
Calculators, template engines, query languages, config formats and compilers all start the same way: turn a string of characters into a list of **tokens** — the words of the language. This step is called **lexing** or **tokenizing**, and it is what makes the next step (parsing) manageable, because the parser no longer has to think about spaces or how many digits a number has.

For the expression `max(x, 2.5) * 3`:

```
name max · op ( · name x · op , · num 2.5 · op ) · op * · num 3 · end
```

The standard technique is a loop with a **position index**. Look at the character at `i` and decide what kind of token starts there:

- whitespace → skip it;
- a digit → keep consuming digits (and one optional `.` followed by digits), then convert the text with `Number`;
- a letter or `_` → consume letters, digits and `_`: a name;
- one of the operator characters → a one-character token;
- anything else → a **syntax error that says where**.

A sticky regular expression (`/…/y`, which only matches exactly at `lastIndex`) is a compact way to do this, but a hand-written loop is just as good and easier to debug:

```js
const isDigit = (c) => c >= '0' && c <= '9'
isDigit('7')    // true
isDigit('x')    // false
```

Two design decisions make the parser's life easier. First, give every token a `type` and a `value`, so the parser can ask "is this an `op` whose value is `(`?". Second, finish the list with a special **end** token, so the parser can always look at "the current token" without checking whether it has run off the end of the array.

=== js4-10 | A recursive-descent parser and evaluator
--- teach
With tokens in hand, you need to understand their **structure**: in `1 + 2 * 3` the `*` binds tighter than the `+`. The classic hand-written technique is **recursive descent**: write one function per level of precedence, from loosest to tightest, each calling the next level for its operands. The grammar for arithmetic:

```
expr  := term  (('+' | '-') term)*
term  := unary (('*' | '/') unary)*
unary := '-' unary | power
power := atom ('^' unary)?
atom  := number | name | name '(' args ')' | '(' expr ')'
```

Read it top down: an expression is terms joined by `+`/`-`; a term is unary pieces joined by `*`/`/`; and so on. Each rule becomes a function:

- `(… )*` becomes a **loop**, which makes the operator **left-associative**: `10 - 4 - 3` is `(10 - 4) - 3`.
- `power` calls `unary` on its right-hand side, which calls back into `power` — **recursion** — making `^` **right-associative**: `2 ^ 3 ^ 2` is `2 ^ 9`. Because `unary` sits *above* `power`, `-2 ^ 2` is `-(2 ^ 2)`, as in mathematics.
- `atom` handles the base cases, and a parenthesised expression restarts at the top with `expr`.

The functions share a position in the token array. Two small helpers keep them readable: `peek()` returns the current token, and `expect(value)` consumes the current token if it is that operator — or throws a `SyntaxError` naming what it found.

This version **evaluates as it parses**: each function returns a number. (A compiler would return tree nodes instead and evaluate later, but the shape of the code is identical.)

Finally, after parsing an `expr`, check that you have reached the `end` token. Forgetting this makes `1 2` quietly evaluate to `1`. Good errors matter as much as correct answers: a user who typed `(1 + 2` should hear "unexpected end", not get `NaN`.

const FUNCTIONS = { min: Math.min, max: Math.max, abs: Math.abs, sqrt: Math.sqrt }

function evaluate(src, vars = {}) {
  const tokens = tokenize(src)
  let pos = 0
  const peek = () => tokens[pos]
  const isOp = (value) => peek().type === 'op' && peek().value === value
  const describe = (t) => (t.type === 'end' ? 'end of input' : `"${t.value}"`)
  const expect = (value) => {
    if (!isOp(value)) throw new SyntaxError(`expected "${value}" but found ${describe(peek())}`)
    pos++
  }

  function expr() {
    let value = term()
    while (isOp('+') || isOp('-')) {
      const op = tokens[pos++].value
      const right = term()
      value = op === '+' ? value + right : value - right
    }
    return value
  }

  function term() {
    let value = unary()
    while (isOp('*') || isOp('/')) {
      const op = tokens[pos++].value
      const right = unary()
      if (op === '/' && right === 0) throw new RangeError('division by zero')
      value = op === '*' ? value * right : value / right
    }
    return value
  }

  function unary() {
    if (isOp('-')) {
      pos++
      return -unary()
    }
    return power()
  }

  function power() {
    const base = atom()
    if (isOp('^')) {
      pos++
      return base ** unary()
    }
    return base
  }

  function atom() {
    const t = peek()
    if (t.type === 'num') {
      pos++
      return t.value
    }
    if (t.type === 'name') {
      pos++
      if (isOp('(')) {
        pos++
        const args = []
        if (!isOp(')')) {
          args.push(expr())
          while (isOp(',')) {
            pos++
            args.push(expr())
          }
        }
        expect(')')
        if (!Object.hasOwn(FUNCTIONS, t.value)) throw new ReferenceError(`unknown function: ${t.value}`)
        return FUNCTIONS[t.value](...args)
      }
      if (!Object.hasOwn(vars, t.value)) throw new ReferenceError(`unknown variable: ${t.value}`)
      return vars[t.value]
    }
    if (isOp('(')) {
      pos++
      const value = expr()
      expect(')')
      return value
    }
    throw new SyntaxError(`unexpected ${describe(t)}`)
  }

  const result = expr()
  if (peek().type !== 'end') throw new SyntaxError(`unexpected ${describe(peek())}`)
  return result
}

=== js4-11 | A mini test runner
--- teach
Test frameworks feel like magic, but the core of Jest, Vitest or Mocha fits on one screen, and building it shows you what the familiar `describe`/`it`/`expect` really do.

**Collecting, then running.** `describe(name, fn)` does not test anything: it calls `fn` straight away so that the `it` calls inside can **register** themselves, with the describe names pushed onto a stack so each test knows its full name (`'math > adds'`). `it(name, fn)` stores `{ name, fn }` in a list. Only `run()` actually executes the tests — one after another, in the order they were registered.

**Assertions are just functions that throw.** `expect(actual)` returns an object of matchers; each matcher checks something and throws an `Error` with a helpful message if it does not hold:

```js
function expect(actual) {
  return {
    toBe(expected) {
      if (!Object.is(actual, expected)) {
        throw new Error(`expected ${JSON.stringify(actual)} to be ${JSON.stringify(expected)}`)
      }
    },
  }
}
```

So a test passes if its function returns (or its promise fulfils) without throwing, and fails otherwise.

**Isolation.** `run` wraps each test in `try`/`catch` and records the result, so one failure never stops the others. It `await`s each test function, which makes **async tests** work for free — a rejected promise is caught like a throw. The error message is the most important output a test runner produces: "expected 3 to be 4" points straight at the problem; "test failed" wastes the reader's time.

`toBe` compares identity (`Object.is`), so it is for primitives. `toEqual` compares **structure**, which needs a deep comparison — key order must not matter. `toThrow` takes a *function* (not the result of calling it) and checks that calling it throws — the classic mistake is writing `expect(parse('{')).toThrow()`, which throws before `expect` is even called.
--- task

- `it(name, fn)` — registers a test; `fn` may be async.
- `expect(actual)` returning matchers that throw an `Error` on failure:
  - `toBe(expected)` — `Object.is`; message `'expected <actual> to be <expected>'`, both written with `JSON.stringify`.
  - `toEqual(expected)` — deep equality of primitives, arrays and plain objects, key order ignored.
  - `toThrow()` — `actual` is a function; fails unless calling it throws.

=== js4-12 | Performance: from quadratic to linear
--- teach
Code that is correct on ten items can be useless on a hundred thousand. The tool for predicting this is **Big-O**: how the work grows as the input grows.

- **O(n)** — one pass. Ten times the data, ten times the time.
- **O(n²)** — a loop inside a loop over the same data. Ten times the data, a **hundred** times the time. 200,000 items means 40 billion steps: minutes, or a frozen browser tab.

The trouble is that the inner loop is often **hidden inside a method call**. Every one of these walks the array:

```js
const arr = [1, 2, 3]
arr.includes(3)           // looks at every item
arr.indexOf(3)            // same
arr.filter((x) => x > 1)  // visits every item, builds a new array
arr.slice(0, 2)           // copies items
```

So `for (const x of items) if (seen.includes(x)) …` is O(n²), and so is `users.map((u) => events.filter((e) => e.user === u))`. Other hidden loops: `find`, `some`, `splice`, `shift`/`unshift` (they move everything), and spreading an accumulator (`acc = [...acc, x]`) inside `reduce`.

The standard cure is to **trade memory for time**: build a `Set` or `Map` in one pass, then answer each question with a single lookup.

- "Have I seen this before?" → a `Set` of what you have seen.
- "What is the best/latest item per key?" → a `Map` from key to the best so far, updated in one pass.
- "How many earlier items pair with this one?" → a `Map` from value to how many times you have seen it.

**Measure, do not guess**: wrap a call in `performance.now()` before and after, and try it at sizes 1,000, 10,000 and 100,000. If each tenfold step costs a hundredfold more time, you have found an O(n²) — and that is where to look.

When you optimise, keep the behaviour **identical**, including the details: which element is "first", what happens on ties, what an empty input returns. The checks on small inputs are there to make sure the fast version still answers the same question.
--- task
All three functions in the starter are correct, but quadratic. Make each one a single pass (O(n)) with the same results:

- `firstRepeat(items)` — the first item that has appeared earlier in the array, or `undefined`.
- `latestPerUser(events)` — events are `{ user, time }`. One event per user — the one with the greatest `time` (on a tie, the earlier event in the array) — in the order each user first appears.
- `countPairsWithSum(nums, target)` — how many index pairs `i < j` have `nums[i] + nums[j] === target`.

Each will be given 200,000 items.

=== js4-13 | Debugging: the out-of-order response
--- teach
Here is a bug that passes every test on a fast machine and shows up only in production: a search box shows results for **"a"** while the box says **"ab"**.

The code is innocent-looking:

```js
async function type(query) {
  state.query = query
  state.results = await api(query)
}
```

The hidden assumption is that **responses arrive in the order requests were sent**. They do not. The request for "a" matches more rows and is slower; the request for "ab" is sent 5ms later but answers first. So "ab"'s results arrive, then "a"'s results arrive and **overwrite** them. The same race breaks loading spinners (the first response to arrive switches the spinner off while the latest request is still running) and error messages (a stale failure replaces fresh results).

How to debug a race like this:

1. **Make timing controllable.** Replace the real API with a fake whose delays you choose, so the bad interleaving happens every time, not one run in fifty.
2. **Log with identities.** Give each request a number and log `start #1 a`, `start #2 ab`, `done #2`, `done #1`. The order of the "done" lines is the smoking gun.
3. **Name the invariant.** "The results on screen always belong to the latest query."
4. **Enforce it at the point of writing**, not by adding delays.

The standard fix is a **request counter**: each call takes `const id = ++latest`, and after every `await` it checks `if (id !== latest) return` before touching shared state. Only the most recent request may write. Apply the same check to the loading flag and to errors — every piece of state the request writes.

In a browser you would also cancel the stale request with an `AbortController` to save bandwidth — but cancelling is an optimisation. The counter check is what makes the state correct, because a response can still arrive after you tried to cancel it.

Never "fix" a race with `setTimeout` or a longer delay. That only changes which interleaving is rare.

=== js4-14 | Generators as coroutines
--- teach
So far generators have only handed values **out**. But `next(value)` can also send a value **in**: it becomes the result of the `yield` expression the generator is paused at. A function that can pause, receive a value, and carry on is a **coroutine**.

```js
function* greeter() {
  const name = yield 'What is your name?'
  const mood = yield `Hi ${name}! How are you?`
  return `Glad you are ${mood}.`
}
const g = greeter()
g.next().value          // 'What is your name?' — runs to the first yield
g.next('Ada').value     // 'Hi Ada! How are you?' — 'Ada' became the first yield's value
g.next('well').value    // 'Glad you are well.'
```

Notice the first `next()` carries no value: it only starts the generator and runs it up to the first `yield` (this is called **priming**). There is also `g.throw(err)`, which resumes the generator by throwing `err` *at* the paused `yield` — so a `try`/`catch` inside the generator can handle it.

Coroutines let you write something stateful — a running average, a parser, a game loop — as straight-line code that keeps its variables between inputs.

They are also how `async`/`await` was prototyped. Imagine a generator that `yield`s promises. A small **runner** takes each yielded promise, waits for it, and sends the result back in with `next(result)` — or, if it rejected, calls `throw(error)` on the generator. From the generator's point of view, `const user = yield fetchUser(1)` reads exactly like `const user = await fetchUser(1)`. Libraries such as `co` and redux-saga work this way, and it is still useful whenever you want to control *how* the waiting happens — to cancel, retry, log, or test async flows without real time.

The runner's loop, in words: call `step = gen.next(value)` (or `gen.throw(error)`); if `step.done`, fulfil with `step.value`; otherwise wait for `step.value` (wrap it in `Promise.resolve` so plain values work too), then loop with the outcome. If `next` or `throw` itself throws — the generator did not catch it — reject.

- `run(genFn, ...args)` — calls `genFn(...args)` to get a generator and drives it: each yielded value is awaited (plain values too) and sent back in; a rejection is thrown into the generator with `throw`. Returns a promise that fulfils with the generator's return value, or rejects if the generator throws an error it does not catch.

function* averager() {
  let total = 0
  let count = 0
  let n = yield null
  while (true) {
    total += n
    count++
    n = yield total / count
  }
}

function run(genFn, ...args) {
  return new Promise((resolve, reject) => {
    let gen
    try {
      gen = genFn(...args)
    } catch (err) {
      reject(err)
      return
    }
    function step(method, input) {
      let result
      try {
        result = gen[method](input)
      } catch (err) {
        reject(err)
        return
      }
      if (result.done) {
        resolve(result.value)
        return
      }
      Promise.resolve(result.value).then(
        (value) => step('next', value),
        (error) => step('throw', error),
      )
    }
    step('next', undefined)
  })
}
