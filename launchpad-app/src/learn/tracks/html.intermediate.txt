=== web2-01 | Semantic HTML and landmarks
--- teach
The basics built pages from headings, lists, a form, some CSS and a few lines of JavaScript. This course makes them real pages: markup that means something to everyone who uses it, CSS you can reason about instead of guess at, and JavaScript that builds and updates the page from data.

A page built only from `div`s looks fine to someone who can see it and means nothing to everyone else. HTML has elements that say what a region *is*:

| Element   | What it is                                              |
| --------- | ------------------------------------------------------- |
| `header`  | the introduction: logo, site name, often the navigation |
| `nav`     | a block of main navigation links                         |
| `main`    | the page's own content (exactly one per page)            |
| `article` | a self-contained piece: a post, a card, a product        |
| `section` | a themed part of something, usually with a heading       |
| `aside`   | related but secondary: a sidebar, a note                 |
| `footer`  | closing information: copyright, contact, small links     |

```html
<header>
  <h1>Orbit News</h1>
  <nav>
    <ul>
      <li><a href="/">Home</a></li>
      <li><a href="/launches">Launches</a></li>
    </ul>
  </nav>
</header>
<main>
  <article>
    <h2>Rocket lands upright</h2>
    <p>The booster came back on its own.</p>
  </article>
</main>
<footer>© Orbit News</footer>
```

These are called **landmarks**. A screen reader lists them, so someone can jump straight to "main" or "navigation" instead of listening to the whole page. Search engines use them to find the real content, and your CSS gets easier too: `nav a` says far more than `.div3 .inner a`.

They look exactly like a `div` until you style them, so switching costs you nothing visually. Keep `div` for boxes that exist only for layout.

When you are done there should be no `div` left on the page.

=== web2-02 | Accessible forms
--- teach
A form is only as good as its labels and its types. Four habits make one work for everybody:

**1. Every field has a label.** `label for="x"` joined to `id="x"`. The label is read out with the field, and clicking it focuses the field (a bigger target on a phone). A `placeholder` is not a label: it vanishes as soon as someone types.

**2. The right `type`.** `type="email"` brings up the @ keyboard on phones and checks the shape of the address; `type="number"` gives a numeric keypad and accepts `min`, `max` and `step`.

**3. Say what is required.** `required` makes the browser refuse to submit an empty field.

**4. Group related choices.** Radio buttons that answer one question share a `name` and sit in a `fieldset`, whose `legend` is the question:

```html
<fieldset>
  <legend>Seat</legend>
  <input type="radio" id="window" name="seat" value="window">
  <label for="window">Window</label>
  <input type="radio" id="aisle" name="seat" value="aisle">
  <label for="aisle">Aisle</label>
</fieldset>
```

The browser tracks whether each field is currently valid, and CSS can see it: `input:invalid` matches a required field that is empty, an email field holding `not-an-email`, or a number below its `min`. That same state is what stops the form submitting — you get validation without writing any JavaScript.

=== web2-03 | Accessibility: images, headings and links
--- teach
Three quick wins cover a large share of real accessibility problems.

**Alt text says what an image is *for*.** A logo's alt is the name it shows (`alt="Orbit News"`). A photo's alt describes what matters in it. A purely decorative image — a divider, a flourish — gets an *empty* alt, `alt=""`, which tells a screen reader to skip it. A *missing* alt is the worst case: many readers then read out the file name, "divider underscore final dot png".

**Headings are an outline, not a font size.** One `h1`, then `h2` for sections, `h3` inside those. Never skip a level to get smaller text — screen reader users navigate by heading, and a jump from `h1` to `h4` looks like missing sections. If you want smaller text, that is CSS's job.

**Link text makes sense on its own.** People skim a list of a page's links. Five links all saying "click here" are useless; `Read the launch report` says where it goes.

```html
<img src="logo.png" alt="Orbit News">
<img src="swirl.png" alt="">                 <!-- decorative: skip it -->
<h1>Launch week</h1>
<h2>Monday</h2>                              <!-- not h4 -->
<a href="/report">Read the launch report</a> <!-- not "click here" -->
```

3. The link says `click here`. Change its text to `Read the launch report`.

=== web2-04 | Debugging: the button that isn't a button
--- teach
Bug reports about accessibility usually arrive as "it doesn't work for me", so debug them the way you debug anything:

1. **Reproduce it the way they use it.** Put the mouse away. Press Tab to move through the page and Enter or Space to press things. Does focus ever land on the control? Does Enter do anything?
2. **Inspect what the element really is.** In the browser's developer tools, look at the element and its accessibility panel. What role does it have? A `div` has none, so assistive technology announces it as plain text.
3. **Check your assumptions.** "It looks like a button" is an assumption about CSS, not a fact about behaviour.
4. **Fix the cause, not the symptom.** You *could* bolt `tabindex="0"`, `role="button"` and a `keydown` handler for Enter and Space onto the `div`. Or you could use the element that already does all of that: `<button>`. A real button is focusable, is announced as a button, and turns Enter and Space into a `click` — for free.

```html
<!-- looks like a button, is a div: no focus, no keyboard, no role -->
<div class="btn" onclick="save()">Save</div>

<!-- is a button -->
<button class="btn" type="button" onclick="save()">Save</button>
```

When you swap, check the styling still holds: buttons come with a default border and font, which your class may need to reset.

=== web2-05 | Selectors and specificity
--- teach
When two rules set the same property on one element, the browser picks a winner. Knowing how is the difference between guessing and fixing.

**1. Specificity.** Each selector scores three numbers — (ids, classes/attributes/pseudo-classes, elements) — compared left to right:

| Selector           | Score     |
| ------------------ | --------- |
| `a`                | (0, 0, 1) |
| `.active`          | (0, 1, 0) |
| `nav a.active`     | (0, 1, 2) |
| `#menu a`          | (1, 0, 1) |
| `#menu a.active`   | (1, 1, 1) |

One id beats any number of classes. So `#menu a { color: grey }` beats `.active { color: tomato }`, even though `.active` looks more specific *to you*.

**2. Order.** With equal scores, the rule that comes later wins.

**3. Selectors that simply don't match.** `.card > p` means a `p` that is a *direct child* of `.card`; a `p` inside a `div` inside the card is not matched. `.card p` (a space) matches any depth.

**The method.** In developer tools, select the element and open *Computed*: it shows the winning value and, crossed out, the rules that lost. Then fix the cause: make the selector you want at least as specific as the one beating it (`#menu a.active`), or make the loser less specific. `!important` also "works", and it starts an arms race you will lose later — every future override then needs `!important` too.

=== web2-06 | The box model and box-sizing
--- teach
Every box is content, then padding, then border, then margin. The surprise is what `width` means. By default (`box-sizing: content-box`) it is the width of the **content only**, and padding and border are added on top:

```css
.box {
  width: 240px;
  padding: 20px;
  border: 4px solid #1e90ff;
}
/* drawn 240 + 20 + 20 + 4 + 4 = 288px wide */
```

So a layout that "should" fit two 240px boxes in 500px overflows, and every time you change padding, the box grows. The fix almost every modern site uses:

```css
*, *::before, *::after {
  box-sizing: border-box;
}
```

With `border-box`, `width` is the width of the **whole box, border included**: padding and border are taken out of the inside. A 240px box stays 240px whatever padding you give it.

Two more box facts worth knowing:

- **Vertical margins collapse.** A `margin-bottom: 24px` above a `margin-top: 16px` gives a 24px gap, not 40px — the larger wins.
- **Inline elements** (`span`, `a`) ignore `width`, `height` and vertical margins. Give them `display: inline-block` or `block` if you need those.

The script at the bottom of this lesson's page is a ruler: it measures the real, drawn width of the first box and writes it on the page.

=== web2-07 | Flexbox layouts
--- teach
You have used `display: flex` and `gap`. Real layouts need a few more pieces. On the **container**:

- `justify-content` spreads children along the main axis: `flex-start`, `center`, `space-between` (first and last at the edges, the rest spread out), `space-around`.
- `align-items` lines them up across it: `stretch` (the default), `center`, `flex-start`, `baseline`.
- `flex-wrap: wrap` lets children move onto a new line instead of squashing.

On a **child**:

- `flex: 1` lets it grow to share spare space equally with other `flex: 1` siblings. (`flex: 2` takes twice as much.)
- `margin-left: auto` on one child pushes it, and everything after it, to the far end.

The two layouts nearly every site has:

```css
/* A top bar: logo on the left, links on the right, vertically centred */
.bar   { display: flex; justify-content: space-between; align-items: center; }
.links { display: flex; gap: 16px; }

/* A row of equal cards that wrap on small screens */
.cards { display: flex; flex-wrap: wrap; gap: 12px; }
.card  { flex: 1; min-width: 120px; }
```

Flexbox is one-dimensional: it lays things out in a row *or* a column. For rows and columns at once, the next lesson has grid.

=== web2-08 | CSS grid
--- teach
Grid lays things out in rows **and** columns at once, which makes it the tool for whole-page layouts.

```css
.page {
  display: grid;
  grid-template-columns: 200px 1fr;   /* a 200px column, then the rest */
  gap: 16px;
}
```

`fr` is "a fraction of the free space": `1fr 2fr` splits it a third and two thirds, and `repeat(3, 1fr)` makes three equal columns.

The most readable way to place regions is to **name** them and draw the layout as text:

```css
.page {
  display: grid;
  grid-template-columns: 200px 1fr;
  grid-template-areas:
    "header header"
    "side   main"
    "footer footer";
}
.page > header { grid-area: header; }
.page > aside  { grid-area: side; }
.page > main   { grid-area: main; }
.page > footer { grid-area: footer; }
```

Each string is a row, each word a cell. Repeating a name makes that region span cells — the header spans both columns. Every row must have the same number of cells, and each area must be a rectangle.

The HTML order stays the logical reading order (header, sidebar, content, footer); CSS decides where things *appear*. That is a big win for accessibility: screen readers follow the source, not the picture.

=== web2-09 | CSS custom properties
--- teach
A **custom property** (often called a CSS variable) is a value you name once and use everywhere:

```css
:root {
  --brand: #1e90ff;
  --space: 16px;
}
.button {
  background: var(--brand);
  padding: calc(var(--space) / 2) var(--space);
}
```

Names start with `--`. `:root` is the `html` element, so a property set there is available to the whole page. `var(--name, fallback)` uses the fallback if the property is not set.

The feature that makes them more than find-and-replace: **they inherit and can be overridden per element**, like any other CSS property. Change the variable on a class and everything inside picks it up:

```css
.danger { --brand: #dc143c; }   /* every var(--brand) inside turns red */
```

That is how themes work: one set of rules, and a class (or attribute) higher up that swaps the values. JavaScript can change them too — `document.documentElement.style.setProperty('--brand', 'purple')` — and the whole page updates.

The mistake to avoid: overriding the *property* (`.danger { background: red }`) instead of the *variable*. It works for that one rule, and every other place that uses `--brand` (a border, a focus ring) stays blue.

=== web2-10 | Responsive design with media queries
--- teach
One page, every screen. A **media query** wraps rules that apply only when a condition about the screen is true:

```css
.cards { display: flex; gap: 12px; }        /* always */

@media (max-width: 900px) {                 /* only 900px wide or less */
  .cards { flex-direction: column; }
  h1 { font-size: 28px; }
}
```

Rules inside the query override the ones outside because they come later with the same specificity — so put your queries **after** the rules they change.

Two ways to organise it:

- **Desktop first**: write the wide layout, then `max-width` queries that simplify it for smaller screens.
- **Mobile first**: write the narrow layout, then `min-width` queries that add columns as room appears. Many teams prefer this — the phone gets the least CSS to undo.

Pick **breakpoints** where *your* layout breaks, not at particular phone models. And for a real site, put `<meta name="viewport" content="width=device-width, initial-scale=1">` in the `head`, or phones pretend to be a 980px desktop and shrink everything.

The preview here is **800px wide**, so a `max-width: 900px` query is on, and a `min-width: 1000px` query is off. That is what you will design against.

=== web2-11 | Building and changing elements
--- teach
The DOM is a tree of objects you can create, fill and change. The tools you will use every day:

```js
const li = document.createElement('li')   // a new element, not on the page yet
li.textContent = 'Europa Clipper'          // its text — always safe
li.classList.add('done')                   // add / remove / toggle / contains
li.dataset.id = 'm3'                       // becomes the attribute data-id="m3"
li.setAttribute('title', 'Launched 2024')  // any attribute
list.append(li)                            // now it is on the page
li.remove()                                // and now it isn't
```

The task's script uses a few more pieces of JavaScript than the basics did. If any is new, the JavaScript course teaches it properly; the short version:

- An **object** groups named values: `{ id: 'm1', name: 'Apollo 11' }`, and `mission.name` reads one. An array of objects is the usual shape of a list of data.
- `===` compares, strictly: `mission.status === 'done'` is `true` or `false`.
- `array.filter((m) => m.status === 'done')` makes a new array of the items for which the arrow function returns `true`; `.length` counts them.
- A **template literal** uses backticks and puts values inside `${…}`: `` `${done} of ${missions.length} done` ``.

**`textContent`, not `innerHTML`, for data.** `innerHTML` parses its string as HTML, so a name like `<img src=x onerror=…>` becomes a real element — and runs code. That is the classic XSS hole. `textContent` puts the string in as plain text, whatever it contains. Use `innerHTML` only for markup you wrote yourself.

**`dataset`** is how elements carry your own data: `data-id="m3"` in HTML is `el.dataset.id` in JavaScript (and `data-launch-date` is `el.dataset.launchDate`). Later, when someone clicks an item, you read its id straight off the element.

**`classList`** beats assigning `className` because it changes one class without wiping the others: `el.classList.toggle('done', isDone)` adds it when `isDone` is true and removes it when false.

=== web2-12 | Events: click, input and submit
--- teach
Every listener receives an **event object** describing what happened:

```js
button.addEventListener('click', (event) => {
  event.target        // the element that was actually clicked
  event.currentTarget // the element the listener is on
})
```

Which event to listen for matters:

- `click` — a button was pressed (by mouse, or by Enter/Space on a focused button).
- `input` — a field's value changed, on every keystroke.
- `change` — a field's value was committed: a checkbox ticked, a select changed, a text field left.
- `submit` — a **form** was submitted: by clicking its submit button *or* by pressing Enter in one of its fields.

For forms, listen for `submit` on the form, not `click` on the button. You get Enter-to-submit and the browser's built-in validation for free. The one thing you must do: stop the browser's default action, which is to send the form to a server and load a new page:

```js
form.addEventListener('submit', (event) => {
  event.preventDefault()          // stay on this page
  const text = input.value.trim()
  if (!text) return               // ignore empty submissions
  // … use it …
  input.value = ''                // ready for the next one
})
```

`preventDefault()` cancels the browser's default for any event — following a link, ticking a box, submitting a form.

In that handler, `.trim()` removes spaces from both ends of the text; `!text` means "not text", which is true for an empty string; and `return` leaves the function early, so nothing after it runs. To pick between two values in one expression, use `condition ? a : b`: `` n === 1 ? '1 item' : `${n} items` ``.

=== web2-14 | Problem: filter a list as you type

A filter box looks simple and hides several decisions. Work through it like any problem:

**1. Restate it.** As you type, show only the names that contain the text, and say how many are showing.

**2. Examples, including the awkward ones.**

- `an` → Anika, Dana, Ivan, Joanna (anywhere in the name, not just the start)
