=== web3-01 | Event delegation
--- teach
The intermediate course drew pages from data and events. This course is about interfaces that stay correct as they grow: one listener for many elements, state and render, components, your own validation, keyboard and ARIA patterns, timers, and the debugging that goes with them.

From here on, the Web courses use the JavaScript that the JavaScript course's basics teach — functions, objects, arrays with `map`, `filter` and `reduce`, template literals, `async`/`await` — without stopping to explain it. Anything beyond that is explained where it first appears.

Attaching a listener to every item has two problems. It is wasteful on a long list, and — worse — items added later have no listener at all, because the loop that attached them ran once, at the start.

**Event delegation** uses the fact that events *bubble*: a click on a button inside an `li` inside a `ul` fires on the button, then the `li`, then the `ul`, and so on up to `document`. So one listener on the container sees every click inside it, including clicks on elements that did not exist when the listener was added:

```js
list.addEventListener('click', (event) => {
  const del = event.target.closest('.delete')
  if (del) {
    del.closest('li').remove()
    return
  }
  const text = event.target.closest('.text')
  if (text) text.closest('li').classList.toggle('done')
})
```

`event.target` is the innermost element clicked — maybe a `span` or an icon *inside* your button — so don't compare it directly. `target.closest(selector)` walks up from the target to the nearest ancestor (or itself) that matches, and returns `null` if there is none. That one call makes delegation robust.

Two more tools that pair with it: put what the handler needs on the element (`data-id="42"`, read as `el.dataset.id`), and check the match is inside your container (`list.contains(el)`) when containers are nested.

=== web3-02 | State and render
--- teach
Once a page does more than one thing, "change the DOM whenever something happens" falls apart. The Play button's text, the status line, the highlighted song and the disabled buttons all depend on the same two facts — which song, and whether it is playing — and every handler has to remember to update all of them.

The pattern every modern framework is built on:

1. **One state object** holds the facts. Only the facts: `{ current: 0, playing: false }`. Not "the text of the button" — that is derived.
2. **One `render()` function** makes the whole view match the state. It never reads the page to decide anything; it only writes.
3. **Handlers only change state, then call `render()`.**

```js
const state = { count: 0 }

function render() {
  countEl.textContent = state.count
  minus.disabled = state.count === 0
}

plus.addEventListener('click', () => { state.count += 1; render() })
minus.addEventListener('click', () => { state.count -= 1; render() })

render()   // draw the starting state once
```

Now "is the minus button disabled at zero?" has exactly one answer, in one place. Adding a feature means adding state and a line in `render()`, not hunting through every handler. And bugs become reproducible: the same state always draws the same page.

Rebuilding a small list inside `render()` each time is fine: `list.replaceChildren(...items)` swaps all the children in one go. (`...items` spreads the array into separate arguments, like `Math.min(...numbers)`. And `map` hands your function each item's position as a second argument: `songs.map((title, i) => …)`.) (For big lists, the expert course shows how to update in place.)

=== web3-03 | Components: functions that return elements
--- teach
Building elements by hand — `createElement`, set this, append that — gets long fast. Two small ideas tidy it up.

**A helper that builds an element in one call:**

```js
function h(tag, attrs = {}, ...children) {
  const el = document.createElement(tag)
  for (const [key, value] of Object.entries(attrs)) {
    if (key === 'class') el.className = value
    else if (key.startsWith('on')) el.addEventListener(key.slice(2), value)
    else el.setAttribute(key, value)
  }
  el.append(...children.flat())   // strings become text, safely
  return el
}

h('p', { class: 'note' }, 'Hello')             // <p class="note">Hello</p>
h('button', { onclick: () => alarm() }, 'Go')   // a button with a click listener
```

`append` accepts strings and inserts them as text (never HTML), and `children.flat()` lets you pass an array of children, such as the result of `map`. Two newer pieces of JavaScript here: `...children` in the parameter list is a **rest parameter**, which collects every argument after the first two into an array; and `Object.entries(attrs)` gives the object's `[key, value]` pairs, which `for (const [key, value] of …)` unpacks into two variables.

**Components: functions from data to elements.**

```js
function Badge(label) {
  return h('span', { class: 'badge' }, label)
}
function Mission(m) {
  return h('li', { 'data-id': m.id }, m.name, ' ', Badge(m.status))
}
list.append(...missions.map(Mission))
```

Each component takes data and returns an element; bigger components are built from smaller ones. The shape of the page is now readable in the code, and a component can be reused anywhere. This is exactly what React's JSX turns into: `<Badge label="x" />` compiles to a call much like `h(Badge, …)`.

Behaviour can live inside a component too: an `onclick` in the attributes remembers that component's own variables (a **closure** — the stale-closures lesson looks at them closely), so each card handles its own button.

=== web3-04 | Form validation with your own messages
--- teach
The browser's built-in validation is a good floor, but its bubbles differ in every browser and can't be styled. To show your own messages, keep the rules in HTML (`required`, `type="email"`) and take over the reporting:

```html
<form id="signup" novalidate>          <!-- novalidate: "I'll report errors" -->
  <label for="email">Email</label>
  <input id="email" type="email" required aria-describedby="email-error">
  <p id="email-error" class="error"></p>
</form>
```

Every field has a `validity` object telling you exactly what is wrong:

```js
email.validity.valueMissing   // required, but empty
email.validity.typeMismatch   // not shaped like an email
email.validity.valid          // no problems at all
```

On submit, work out each field's message, show it, and mark the field:

- `aria-invalid="true"` tells assistive technology the field is in error, and `aria-describedby` points at the message element, so the message is read out along with the field.
- Move focus to the **first** invalid field, so keyboard and screen reader users land where the problem is.
- Only when there are no errors, do the real work.

One trap: `minlength` only reports `validity.tooShort` after a **person** has edited the field. A value set by script — autofill, a test, your own code — is never "too short" as far as `validity` is concerned. For lengths, check `value.length` yourself.

And a design point: say how to fix it. "Invalid input" is useless; "Use at least 8 characters." is an instruction.

Two pieces of JavaScript that help: `array.find(fn)` returns the first item for which `fn` returns true (or `undefined` if none does), and `a || b` gives `b` when `a` is empty or missing, as in `errors[name] || ''`.

=== web3-05 | Keyboard access and ARIA: a disclosure
--- teach
A **disclosure** is a control that shows and hides a section: an FAQ answer, a "More details" panel. Getting it right takes three things.

**1. The control is a `button`.** It is focusable, and Enter and Space press it, with no extra code.

**2. It says whether it is open.** `aria-expanded="true"` or `"false"` on the button is announced as "expanded" or "collapsed". `aria-controls` names the id of the panel it opens.

**3. The panel is really hidden when closed.** The `hidden` attribute removes it from the page *and* from the accessibility tree, so a screen reader doesn't read hidden answers.

```html
<h3>
  <button id="q1" aria-expanded="false" aria-controls="a1">How long is the flight?</button>
</h3>
<div id="a1" hidden>About three days.</div>
```

```js
button.addEventListener('click', () => {
  const open = button.getAttribute('aria-expanded') === 'true'
  button.setAttribute('aria-expanded', String(!open))
  panel.hidden = open
})
```

Notice the source of truth: the button's `aria-expanded` *is* the state, and the panel follows it. Keep them changing together, in one function, or they will disagree.

**ARIA's first rule:** if a native element does the job, use it. ARIA only changes what is *announced*; it adds no behaviour. `role="button"` on a `div` makes a screen reader say "button", but the div still can't be focused or pressed with Enter. (For a zero-JavaScript version, `<details><summary>` is a native disclosure — worth knowing, though it is harder to style and control.)

=== web3-06 | Timers and asynchronous UI
--- teach
Real interfaces wait: for a save, a network reply, an animation. `setTimeout(fn, ms)` runs `fn` once, later, and returns an id you can cancel with `clearTimeout(id)`. `setInterval` repeats until `clearInterval`.

```js
const id = setTimeout(() => console.log('later'), 500)
clearTimeout(id)   // changed my mind: it never runs
```

Wrapped in a promise, a delay reads like ordinary code with `async`/`await`:

```js
const sleep = (ms) => new Promise((resolve) => setTimeout(resolve, ms))

async function save() {
  button.disabled = true
  show('Saving...')
  await sleep(300)          // stand-in for a request to a server
  show('Saved')
  button.disabled = false
}
```

Design the **states**, not just the happy path: idle → saving → saved → idle. While saving, disable the button so a second click can't start a second save. Put the message in an element with `role="status"` so screen readers announce it without moving focus.

**The classic timer bug:** a message that clears itself "after one second" — using a timer scheduled for an *earlier* message. Save, then save again 800ms later: the first save's clear-timer fires and wipes the second save's "Saved" early. The fix is to keep the timer's id and cancel the old one before scheduling a new one:

```js
let clearTimer = null
function flash(text) {
  show(text)
  clearTimeout(clearTimer)                       // cancel any pending clear
  clearTimer = setTimeout(() => show(''), 1000)
}
```

"I click the button and nothing happens" has a short list of causes, and a method finds the right one in a minute.

**1. Look at the console first.** Nothing happening often means an error happened — earlier, when the page loaded, not when you clicked. Here it would say:


=== web3-08 | Debugging: the lost `this`
--- teach
Classes are a tidy way to build widgets: each instance keeps its own state and its own elements. They also bring the most common JavaScript surprise.

If classes are new to you: a `class` is a blueprint for objects. `new Counter(root)` makes a new object and runs its `constructor`; methods such as `increment()` are shared by every counter; and inside them `this` is meant to be the object the method belongs to, so `this.count` is that counter's own number. (The JavaScript course covers classes in depth.)

```js
class Counter {
  constructor(root) {
    this.count = 0
    root.querySelector('.inc').addEventListener('click', this.increment)
  }
  increment() {
    this.count += 1   // TypeError, or NaN — what is `this` here?
  }
}
```

**`this` is decided by how a function is *called*, not where it was written.** `counter.increment()` sets `this` to `counter`. But passing `this.increment` to `addEventListener` hands over the bare function; later the browser calls it with `this` set to the element the listener is on — the button. `this.count` is then the button's `count` (undefined), and `this.render()` fails with *"this.render is not a function"*.

**Method:** when a method misbehaves only as a callback, log `this` at the top of it: `console.log(this)`. If you see `<button>`, you have found it.

**Fixes**, all common in real code:

```js
// 1. An arrow function: arrows have no `this` of their own and use the surrounding one
button.addEventListener('click', () => this.increment())

// 2. Bind once in the constructor
this.increment = this.increment.bind(this)

// 3. A class field holding an arrow function
increment = () => { this.count += 1; this.render() }
```

Knowing *why* matters more than the fix: the same bug appears with `setTimeout(this.tick, 1000)` and `array.map(this.format)`.

=== web3-09 | Debugging: stale closures
--- teach
A function remembers the variables around it where it was created — that is a **closure**. It remembers the *variable*, not the value it had at the time, and that difference causes two famous bugs.

**Bug 1: one shared loop variable.** `var` is scoped to the whole function (or script), so every handler created in this loop shares *one* `i`:

```js
for (var i = 0; i < buttons.length; i++) {
  buttons[i].addEventListener('click', () => pick(sizes[i]))
}
```

By the time anyone clicks, the loop has finished and `i` is `3`, so `sizes[3]` is `undefined` for every button. With `let`, each iteration gets a fresh `i`, and each handler remembers its own. (`buttons.forEach((b, i) => …)` also gives each its own.)

**Bug 2: a snapshot that goes stale.** A value copied into a variable once, at setup, never changes when the thing it came from does:

```js
let selected = 'S'
const price = prices[selected]    // computed once, now, for 'S'
function showPrice() {
  priceEl.textContent = '$' + price   // always the price of S
}
```

The fix is to compute from the current state at the moment you need it: `prices[selected]` inside `showPrice`.

**Method:** log inside the handler, at click time — `console.log(i, selected, price)`. Stale-closure bugs are obvious once you see the values *when the code runs* rather than imagining them from when it was written.

=== web3-10 | A tabs widget
--- teach
Tabs are a widget with a precise, well-known contract, so screen reader users know how to drive them. The roles:

```html
<div role="tablist" aria-label="Mission">
  <button role="tab" id="tab-1" aria-controls="panel-1" aria-selected="true" tabindex="0">Crew</button>
  <button role="tab" id="tab-2" aria-controls="panel-2" aria-selected="false" tabindex="-1">Rocket</button>
</div>
<div role="tabpanel" id="panel-1" aria-labelledby="tab-1">…</div>
<div role="tabpanel" id="panel-2" aria-labelledby="tab-2" hidden>…</div>
```

- The selected tab has `aria-selected="true"`, the others `"false"`; only the selected tab's panel is visible.
- **Roving tabindex:** only the selected tab has `tabindex="0"`; the others have `-1`. So Tab moves *into* the tab list once and then on to the panel, rather than through every tab.
- **Arrow keys** move between tabs: Right to the next, Left to the previous, wrapping around; Home to the first, End to the last. Moving also selects, and moves focus.

Write it as one function that selects a tab by index and updates *everything* — that is the state-and-render idea on a small scale:

```js
function select(index) {
  tabs.forEach((tab, i) => {
    const on = i === index
    tab.setAttribute('aria-selected', String(on))
    tab.tabIndex = on ? 0 : -1
    panels[i].hidden = !on
  })
}
```

Three pieces of JavaScript in the solution: `[...document.querySelectorAll('[role=tab]')]` copies the page's list into a real array, so `map` works on it; `forEach((tab, i) => …)` runs once per item, with its index; and `key in object` is true when the object has that key.

Keys arrive as `keydown` events; `event.key` is `'ArrowRight'`, `'ArrowLeft'`, `'Home'`, `'End'`. Wrapping is modular arithmetic: `(i + 1) % n` for next, `(i - 1 + n) % n` for previous.

=== web3-11 | A modal dialog
--- teach
A **modal** dialog blocks the rest of the page until it is answered. Building one from `div`s means trapping focus, handling Escape, hiding the rest of the page from screen readers and restoring focus afterwards — easy to get subtly wrong. The `<dialog>` element does most of it for you:

```html
<dialog id="confirm" aria-labelledby="confirm-title">
  <h2 id="confirm-title">Delete this mission?</h2>
  <form method="dialog">
    <button value="cancel">Cancel</button>
    <button value="delete">Delete</button>
  </form>
</dialog>
```

- `dialog.showModal()` opens it as a modal: the rest of the page becomes inert, focus moves inside, and Escape closes it.
- A `<form method="dialog">` inside closes the dialog when submitted, and sets `dialog.returnValue` to the `value` of the button that was pressed. No JavaScript needed for the buttons.
- `dialog.close(value)` closes it from code; the dialog fires a `close` event however it was closed.
- When it is open it has the `open` attribute, which CSS and tests can see.

So the logic lives in one place — the `close` handler reads `returnValue` and acts.

**Two things to get right yourself.**

1. `returnValue` **keeps its old value**. If one opening ended with "delete" and the next is dismissed without a button (Escape, or your own × button calling `close()`), `returnValue` still says "delete". Reset it to `''` each time you open.
2. **Put focus back** on the control that opened the dialog when it closes, so keyboard users continue where they were.

The `close` event is fired just after the dialog closes (as a separate task), so code in the handler runs a moment later, not inside the button's click.

=== web3-12 | Sorting and filtering a table
--- teach
A sortable, filterable table is a small data app: some rows, and a view of them that depends on choices the user makes. Keep those apart.

```js
const state = { sortKey: null, dir: 'asc', query: '' }

function visibleRows() {
  const q = state.query.trim().toLowerCase()
  const rows = planets.filter((p) => p.name.toLowerCase().includes(q))
  if (!state.sortKey) return rows
  const sign = state.dir === 'asc' ? 1 : -1
  return [...rows].sort((a, b) => compare(a[state.sortKey], b[state.sortKey]) * sign)
}
```

The data never changes; `visibleRows()` *derives* what to show from the data plus the state, and `render()` draws it. Filtering and sorting then combine for free.

**Comparing correctly.** `array.sort()` with no comparator compares as **strings**: `[1, 146, 16, 2].sort()` gives `[1, 146, 16, 2]` — "146" comes before "16" alphabetically. For numbers use `a - b`. For text use `a.localeCompare(b)`, which handles case and accents properly. A small helper covers both:

```js
const compare = (a, b) => (typeof a === 'number' ? a - b : String(a).localeCompare(String(b)))
```

`sort` also changes the array in place, which is why the code above sorts a copy (`[...rows]`).

**Accessible sorting.** Put a `button` inside each sortable header, and set `aria-sort="ascending"`, `"descending"` or `"none"` on the `th`, so a screen reader announces how the table is sorted.

**The interaction:** clicking a new column sorts it ascending; clicking the same column again flips the direction.

- typing in `#filter` shows only planets whose name contains the text (ignoring case), still in the chosen order

=== web3-13 | Design: separate data, rendering and events
--- teach
Here is a smell you will meet in almost every older codebase: **the page is the database.** A handler reads a number out of a `span` with `parseInt`, adds one, writes it back, then loops over the whole page to recompute a total from the text of other spans. It works — until someone changes the markup, or formats the number as `1,024`, or you need the same number somewhere else.

The shape that scales has three separate parts:

1. **Data** — a state object, the single source of truth. Plain values: `{ options: [{ id: 'mars', name: 'Mars', votes: 0 }, …] }`.
2. **Rendering** — `render()` draws everything from the state. Totals and "who's leading" are *computed* from the state inside it, never stored separately and never read back from the page.
3. **Events** — handlers translate what the user did into a change of state (`vote('mars')`), then call `render()`. With delegation, one listener covers the whole list.

```js
function vote(id) {
  state.options.find((o) => o.id === id).votes += 1
  render()
}

list.addEventListener('click', (event) => {
  const li = event.target.closest('li')
  if (event.target.closest('.vote') && li) vote(li.dataset.id)
})
```

You know the refactor worked when a new feature is small. A "Reset" button in the old version means another block of DOM-poking; in the new one it is two lines: set every `votes` to 0, call `render()`.

Refactor safely: the page must behave exactly as before at every step. Keep the checks in mind — same ids, same classes, same text.

- a `const state` holds the options and their votes; nothing reads numbers back out of the page (`parseInt` and friends must go)
- a `function render()` builds `#options` from the state (each `li` with `data-id`, a `.name`, a `.votes` count and a `.vote` button), and sets `#total` (`Total: 3`) and `#leader` (`Leader: Moon`, or `Leader: none` with no votes; on a tie the option listed first leads); the leading `li` gets the class `leading`

=== web3-14 | Problem solving: an autocomplete you can drive with the keyboard
--- teach
An autocomplete (a *combobox*, in ARIA terms) is a text field with a list of suggestions. It is a good test of everything in this course, because the hard part is not the matching — it is the state.

**Restate.** As you type, suggest up to five cities that *start with* the text. The arrow keys move a highlight through the suggestions; Enter picks the highlighted one; Escape closes the list; clicking a suggestion picks it too.

**Find the state.** Only two facts: the current `suggestions` (an array) and the `active` index (`-1` for none). Everything on screen — which `li` is highlighted, the field's ARIA attributes — is drawn from those two by `render()`.

**The keys, as state changes:**

| Key       | Change                                                     |
| --------- | ---------------------------------------------------------- |
| ArrowDown | `active = (active + 1) % n` (from -1 this gives 0)         |
| ArrowUp   | `active = active <= 0 ? n - 1 : active - 1`                |
| Enter     | if `active >= 0`: put that city in the field, clear the list |
| Escape    | clear the list                                             |

Call `event.preventDefault()` for the keys you handle, so ArrowUp doesn't also move the text cursor.

**The ARIA contract.** Focus stays in the text field the whole time; the highlight is *virtual*. So the field tells assistive technology which option is highlighted with `aria-activedescendant="opt-2"` (the highlighted `li`'s id), and whether the list is open with `aria-expanded`. Each `li` has `role="option"` and `aria-selected="true"` when highlighted.

**Edge cases:** an empty field suggests nothing; no match means no list (and `aria-expanded="false"`); arrows do nothing with an empty list; a new keystroke resets the highlight.
--- task

- on input: up to 5 cities starting with the trimmed text (ignoring case), in list order, as `li`s with `role="option"` and ids `opt-0`, `opt-1`, …; nothing for an empty field; the highlight resets
- `#city` has `aria-expanded` `true` when there are suggestions, `false` otherwise
- ArrowDown / ArrowUp move the highlight, wrapping around: the highlighted `li` has the class `active` and `aria-selected="true"`, and `#city`'s `aria-activedescendant` is its id
- Enter picks the highlighted city (it goes in the field and the list empties); Escape empties the list; clicking a suggestion picks it

  function render() {
    list.replaceChildren(
      ...suggestions.map((city, i) => {
        const li = document.createElement('li')
        li.id = `opt-${i}`
        li.setAttribute('role', 'option')
        li.textContent = city
        li.classList.toggle('active', i === active)

      }),

    render()

    render()

    const li = event.target.closest('li')
