=== web-01 | Your first page
--- teach
This is the first web course. If you did the Terminal course, you already know that a file is a named box of text. A web page is exactly that: a text file. What makes it a page is the way the text is written. This lesson shows you how to write one, and you will see it drawn on screen as you go.

Think of a newspaper editor with a pen. Before a story goes to print, the editor writes small notes in the margin: "headline" next to the big line at the top, "paragraph" next to each block of text. The printer reads those notes and sets each piece in the right size. A web page works the same way, except the notes sit inside the text, and the printer is your web browser.

### Tags say what each piece is

A web page is written in **[[HTML|html-name]]** — the language that labels each piece of a page. The labels are called **tags**. A tag is a name between angle brackets: the less-than sign `<` and the greater-than sign `>`.

Most labels come in pairs. The **opening tag** `<h1>` says "a main heading starts here". The **closing tag** `</h1>` says "the main heading stops here". The closing tag is the same name with a forward slash `/` in front of it.

```html
<h1>Weather Report</h1>
```

Read that line from left to right:

- `<h1>` opens a main heading. `h1` is short for "heading, level one".
- `Weather Report` is the text inside it. This is what you see on the page.
- `</h1>` closes the heading.

The whole thing — opening tag, text, closing tag — is called an **element**. You never see the tags on the page. The browser reads them, then draws the text inside as a big, bold heading.

### Paragraphs

The tag for a paragraph — an ordinary block of text — is `p`:

```html
<p>Rain is expected after lunch.</p>
```

A paragraph is drawn in normal-sized text, with a little space above and below it.

### The browser draws them in order

A **[[browser|browser]]** is the program that shows web pages: Chrome, Firefox, Safari and Edge are all browsers. It reads your HTML from the top of the file to the bottom and draws each element in that order, one under the other.

```html
<h1>Harbour News</h1>
<p>Two ships came in today.</p>
<p>The lighthouse lamp was cleaned.</p>
```

That draws a big heading, then one paragraph, then a second paragraph under it. On this page, the **Preview** tab shows what the browser draws each time you run your code.

### Spaces and new lines in your code do not show

Here is a surprise. The browser treats every run of spaces and new lines in your text as **[[one single space|whitespace]]**. These two paragraphs look exactly the same on the page:

```html
<p>Clear skies tonight.</p>
<p>Clear
     skies    tonight.</p>
```

**Watch out:** pressing Enter in your code does not start a new line on the page. If you want two separate blocks of text, give each one its own `<p>…</p>`.

### Comments: notes the browser skips

A **comment** is a note for people reading the code. The browser skips it and never shows it. It starts with `<!--` (less-than, exclamation mark, two dashes) and ends with `-->` (two dashes, greater-than):

```html
<!-- The forecast is updated every morning -->
<p>Sunny spells.</p>
```

Only `Sunny spells.` appears on the page. Everything between `<!--` and `-->` is hidden, even if it looks like tags. That is handy for switching a piece of a page off for a while without deleting it. Engineers [[use comments on purpose|comments]].

### The whole page around it

A complete HTML file has a few more parts around your headings and paragraphs:

```html
<!doctype html>
<html>
  <head>
    <title>Harbour News</title>
  </head>
  <body>
    <p>Two ships came in today.</p>
  </body>
</html>
```

From the top:

- `<!doctype html>` is the first line of every page. It tells the browser "this is a modern HTML page". It has no closing tag. Read more in the note on the **[[doctype|doctype]]**.
- `<html>` … `</html>` wraps the whole page.
- `<head>` … `</head>` holds facts *about* the page that are not drawn on it.
- `<title>` … `</title>`, inside the head, is the page's name. It shows on the browser tab, not on the page.
- `<body>` … `</body>` holds everything that is drawn: your headings and paragraphs.

Notice that elements can sit *inside* other elements: the `title` is inside the `head`, which is inside the `html`. Always close the inner one before the outer one. This nesting builds the page into a **[[family tree|tree]]**.

The Preview on this page adds the doctype, `html`, `head` and `body` for you when you leave them out, so short exercises can skip them. A real file you save and open in a browser should always have them.

**Watch out:** the most common mistake is a missing closing tag. If you write `<h1>Weather Report` and forget `</h1>`, the heading never ends: everything after it, paragraphs included, becomes part of the heading and is drawn huge. When a page suddenly looks wrong from one point down, look for an element that was opened and never closed.

::: context html-name What the letters stand for
**HTML** stands for **HyperText Markup Language**. "Markup" is the old printing word for the editor's notes in the margin: you *mark up* text to say how it should be set. "HyperText" means text with links in it, so one page can jump to another; you will write links in lesson 3. The language was invented by Tim Berners-Lee at CERN, the physics laboratory near Geneva, around 1990, so scientists could share papers between computers. Every page on the web is still written in it today.
:::

::: context browser What a browser really does
A browser does three big jobs. It **fetches** the file from a computer somewhere on the internet (or from your own disk). It **reads** the HTML and works out which element is inside which. Then it **draws** them: that step is called **rendering**. The part of the browser that does the reading and drawing is called its **engine**. Chrome and Edge share one engine, Safari has another, and Firefox has a third, which is why a page can look very slightly different in each. The checks in these lessons run your page in a real Chromium engine, the open-source heart of Chrome.
:::

::: context whitespace Why the browser squashes spaces
Spaces, tabs and new lines are called **whitespace**, because they print as nothing but blank paper. The browser squashes each run of them into one space on purpose. It means you can lay out your code however reads best — long lines broken up, inner elements indented — without changing what the visitor sees. Programmers rely on this all the time: the solution to every exercise in this course is indented for people, and the indentation never shows on the page.
:::

::: context comments Comments in real web work
Teams use HTML comments to label big parts of a page (`<!-- Footer starts here -->`), to explain something odd, or to switch off a piece while testing. One thing to know: comments are hidden on the page, but not secret. Anyone can see them with the browser's **View Page Source** command, which shows a page's HTML exactly as it arrived. So never put a password or private note in one.
:::

::: context doctype Where the doctype came from
In the 1990s, browsers drew pages in different, inconsistent ways. When the rules were finally written down properly, browsers had to keep old pages working, so they kept two ways of drawing: an old, bug-for-bug compatible one called **quirks mode**, and the modern, standard one. The line `<!doctype html>` at the top is how a page says "use the modern rules". Leave it out and a browser may fall back to quirks mode, where sizes and spacing can come out strangely. That is why every page starts with it.
:::

::: context tree A page is a family tree
Because elements sit inside elements, a page has the shape of a family tree. `html` is at the top. Its two children are `head` and `body`. The `title` is a child of `head`, and each heading and paragraph is a child of `body`. Programmers call this shape a **tree**, and each element in it a **node**. In lesson 10 you will meet the **DOM**, which is this same tree, held in memory, that JavaScript can reach into and change while the page is open.

=== web-02 | Headings and text
--- teach
Last lesson you wrote a main heading with `h1` and blocks of text with `p`. A real page has more shape than that: sections, smaller headings inside them, and words inside a sentence that need to stand out. This lesson gives you all three.

Think of the contents page at the front of a book. There is the book's title, then chapters, then sections inside each chapter. You can see the whole plan at a glance, before you read a word of the story. Headings give a web page the same plan.

### Six levels of heading

HTML has six heading levels, from `h1` to `h6`. The number says how important the heading is, not how big you want it:

- `h1` is the title of the whole page. Use exactly one per page.
- `h2` starts a section of the page.
- `h3` starts a smaller part inside an `h2` section, and so on down to `h6`.

```html
<h1>Garden Diary</h1>
<h2>Spring</h2>
<p>The tulips came up early.</p>
<h2>Summer</h2>
<p>We picked forty tomatoes.</p>
```

The page title, then two sections, each with its own heading and paragraph. The browser draws `h2` smaller than `h1`, and `h3` smaller again.

### The outline

Read only the headings of a page, top to bottom, and you get its **outline**: the plan of the page. People who cannot see the screen use a **[[screen reader|screen-reader]]**, a program that reads the page aloud, and they often jump from heading to heading to find the part they want. [[Search engines|search-engines]] read the outline too, to work out what a page is about.

So keep the levels in order. An `h3` belongs inside an `h2` section, and an `h2` inside the page's `h1`. Do not jump from `h2` straight to `h4`.

**Watch out:** do not choose a heading level because of its size. If you want a heading smaller, that is a job for CSS, which you will meet in lesson 6. The level says where the heading sits in the plan.

### Elements inside a paragraph

Some elements wrap a few words *inside* a paragraph. `strong` marks words that are important. The browser draws them **bold**:

```html
<p>Bring a <strong>warm coat</strong> tonight.</p>
```

`em`, short for emphasis, marks the word you would say with stress if you read the sentence aloud. The browser draws it in *italics*:

```html
<p>I said the <em>blue</em> door, not the red one.</p>
```

Neither one starts a new line. They sit inside the line of text, which makes them **[[inline elements|inline-block]]**, while `h1` and `p` are block elements that each start on a new line. And they mean something, not only a look: a screen reader can change its voice for them, which is [[why they are not called "bold" and "italic"|strong-em]].

### Close the inner element first

When one element sits inside another, it must close before the outer one does. Think of boxes packed inside boxes: you close the small box before you close the big one.

```html
<p>Water the <strong>seedlings</strong> daily.</p>
```

Here `strong` opens and closes, and only then does the `p` close. Writing `<p>…<strong>…</p></strong>` crosses the two. The browser tries to [[repair crossed or unclosed tags|repair]], but its guess is often not what you meant.

**Watch out:** a `strong` you forget to close keeps going. The browser even carries it on into the next paragraph, so text you never meant to stress comes out bold.

### Writing < and & as text

What if your text needs the less-than sign `<` itself? The browser would think a tag is starting. So HTML has short codes for these characters, called **[[character references|entities]]**:

- `&lt;` shows `<` (lt is "less than")
- `&gt;` shows `>` (gt is "greater than")
- `&amp;` shows `&` (amp is "ampersand", the name of the `&` sign)

Each one starts with `&` and ends with a semicolon `;`.

```html
<p>Lesson 1 covered the &lt;p&gt; tag.</p>
<p>Salt &amp; pepper</p>
```

The page shows `Lesson 1 covered the <p> tag.` and `Salt & pepper`. Because `&` starts a code, write a real ampersand as `&amp;` too.

::: context screen-reader How a screen reader moves through a page
A **screen reader** is software that turns a page into speech or into braille for people who are blind or have low vision. Famous ones include JAWS and NVDA on Windows and VoiceOver on Apple devices. Listening to a whole page from the top would take ages, so their users skip: one key jumps to the next heading, another lists every heading on the page. A page with a clean outline is quick to use. A page where the "headings" are only big bold paragraphs gives them nothing to jump to.
:::

::: context search-engines Why search engines care about headings
A **search engine** such as Google sends programs called crawlers to read pages, then decides which pages answer which questions. It cannot see your design, only your HTML. A clear `h1` that says what the page is about, and `h2` headings that name its sections, are some of the plainest clues it gets. Making a page easy for search engines to understand is a whole job, called **SEO**, search engine optimisation, and good headings are its first step.
:::

::: context inline-block Block elements and inline elements
HTML elements come in two everyday kinds. A **block** element, such as `h1`, `h2` or `p`, starts on a new line and takes the full width of the page, like a paragraph in a book. An **inline** element, such as `strong` or `em`, sits inside a line of text and takes only the room its words need, like a highlighted word. You can put inline elements inside a block, but not the other way round: a paragraph cannot go inside a `strong`.

```svg
<svg xmlns="http://www.w3.org/2000/svg" viewBox="0 0 360 120" font-family="Inter, Arial, sans-serif">
  <rect x="10" y="10" width="340" height="30" rx="4" fill="#8fb8f0" stroke="#1f2a44" stroke-width="1.5"/>
  <text x="20" y="30" font-size="13" fill="#1f2a44">h2: a block takes the whole width</text>
  <rect x="10" y="50" width="340" height="60" rx="4" fill="#ffffff" stroke="#1f2a44" stroke-width="1.5"/>
  <text x="20" y="72" font-size="13" fill="#1f2a44">p: a block, with</text>
  <rect x="122" y="59" width="64" height="20" rx="3" fill="#f2b880" stroke="#1f2a44" stroke-width="1"/>
  <text x="154" y="73" font-size="12" text-anchor="middle" fill="#1f2a44">strong</text>

  <text x="20" y="98" font-size="11" fill="#6c7a93">an inline element takes only the room its words need</text>

```
:::

::: context strong-em Why strong, not bold
Old HTML had `<b>` for bold and `<i>` for italic, and they still work. But they only describe a look. `strong` and `em` describe a *meaning*: "this matters" and "say this with stress". That difference matters to anyone not looking at the screen, and to any page that later changes its design: a site can restyle `strong` as red instead of bold, and the meaning stays. Writing HTML that says what things *are*, not how they look, is called **semantic HTML**, and it comes back in the next course.
:::

::: context repair The browser forgives, but guesses
Browsers almost never refuse to show a broken page. The rules for reading HTML include a long list of exactly how to repair mistakes: crossed tags, missing closing tags, elements in odd places. Every modern browser follows the same rules, so the repair is at least the same everywhere. But the browser cannot know what you meant. When a page looks strange, the cause is very often an element the browser closed, or kept open, in a different place from where you thought.
:::

::: context entities Codes for special characters
These codes are officially called **character references**; most people call them **entities**. There are hundreds, for any symbol you cannot type easily: `&copy;` gives the copyright sign ©, `&deg;` the degree sign °, and `&nbsp;` a "non-breaking" space that never lets a line wrap between two words. You only *have* to use the code for `<` and `&` in text, because those two start tags and codes. Writing `&gt;` for `>` is a common habit that keeps things tidy.
:::

=== web-03 | Links and images
--- teach
So far your pages hold headings and text, and they stand alone. This lesson connects them to the rest of the web: links that jump to another page, and pictures.

Think of a book that says "see page 42". You turn to page 42 yourself. A link is the same pointer, except the reader taps it and the browser does the turning.

### A link is an a element

A **link** is written with the `a` tag. The words between the tags are what the reader sees and clicks:

```html
<a href="https://www.nasa.gov">Visit NASA</a>
```

On the page this shows `Visit NASA`, usually blue and underlined. Clicking it opens NASA's website. The tag name `a` is short for **[[anchor|anchor]]**.

### Attributes: extra facts in the opening tag

How does the link know where to go? From `href="https://www.nasa.gov"`. That is an **attribute** — an extra fact about an element, written inside its opening tag. Every attribute has the same shape:

- a name, here `href` (short for "hypertext reference": the address the link points to)
- an equals sign `=`
- the value, in double quotes `"`

An element can have several attributes. Separate them with spaces, in any order. Attributes go only in the opening tag, never in the closing one.

### Full addresses

`https://www.nasa.gov` is a **[[URL|url]]** — the full address of a page on the web. It starts with `https://`, then the name of the website, and it can go on to a page inside that site, such as `https://www.nasa.gov/missions`.

### Links to your own files

Your own website is a folder of files, like the folders you made in the Terminal course. To link from one page to another page in the same folder, you only need the file's name:

```html
<a href="contact.html">Contact</a>
```

That is a **[[relative path|relative-path]]**: a path that starts from the folder the current page is in. Paths work exactly as they did in the terminal:

- `news.html` is a file in the same folder.
- `blog/first.html` is the file `first.html` inside the folder `blog`. The `/` separates a folder from what is inside it.
- `../home.html` is `home.html` in the folder one level up. `..` means "the parent folder".

### Images

An **image** is the `img` element. It is different from everything so far: it has **no closing tag**, because there is no text to wrap. The browser fetches the picture and draws it where the tag stands. HTML calls this kind of element a **[[void element|void]]**.

```html
<img src="harbour.jpg" alt="Fishing boats tied up in the harbour">
```

Two attributes do the work:

- `src`, short for source, is the picture's address. It works like `href`: a full URL, or a path to a file of yours.
- `alt`, short for alternative text, is a short description of the picture in words.

### Always write alt

The **alt text** is what a screen reader says instead of showing the picture. It is also what the browser shows if the picture fails to load. So describe what the picture *shows*, in the way you would describe it over the phone: "Fishing boats tied up in the harbour", not "image" or "photo123".

Some pictures carry no information at all: a decorative line, a background swirl. Give those an empty alt, `alt=""`, with nothing between the quotes. That tells a screen reader to skip the picture. Leaving `alt` out altogether is different, and worse: many screen readers then read out the file name. There is more on [[writing good alt text|alt-text]] in the note.

### Choosing the size

The `width` attribute sets how wide the picture is drawn, in **[[pixels|pixels]]**, without any unit after the number:

```html
<img src="harbour.jpg" alt="Fishing boats tied up in the harbour" width="200">
```

That draws the picture 200 pixels wide, and the browser scales its height to match.

### A picture you can click

Elements can sit inside other elements, as you saw last lesson. Put an `img` inside an `a`, and the picture becomes the link:

```html
<a href="news.html"><img src="paper.png" alt="Today's news"></a>
```

Clicking the picture opens `news.html`. For a picture that is a link, the alt text should say where the link goes.

**Watch out:** the browser does not tell you when you misspell an attribute's name. Write `herf` instead of `href`, or `scr` instead of `src`, and the browser quietly ignores it: the link goes nowhere, or the picture never appears. When a link or an image does nothing, read its attribute names letter by letter.

::: context anchor Why a link is called an anchor
In the first version of HTML, the `a` element did two jobs. It could be the *start* of a link, the bit you click, or the *end* of one, a fixed spot inside a long page that a link could jump to. That fixed spot was the "anchor", like a ship's anchor holding one place. Both jobs kept the same short tag name. Today `a` is almost always the clickable start, and jumping to a spot inside a page is done with an `id`, which you will meet in lesson 5.
:::

::: context url The parts of a URL
**URL** stands for **Uniform Resource Locator**: a standard way of writing where something is. In `https://www.nasa.gov/missions`, the first part, `https`, is the **protocol**: the rules the browser uses to fetch the page. The `s` stands for "secure": the page travels encrypted, so nobody in between can read or change it. After `://` comes the website's name, its **domain**, `www.nasa.gov`. Everything after the next `/` is the **path** to one page inside that site, much like a file path on your own computer.
:::

::: context relative-path Relative and absolute paths
A path that starts from where you are is **relative**: "the file next door". A full address that works from anywhere is **absolute**: `https://www.nasa.gov/missions`. You met the same idea in the terminal, where `notes/todo.txt` started from your current folder but `/home/ada/notes/todo.txt` started from the very top. Websites use relative paths for their own pages, so the whole folder can move to a new computer or a new domain and every link still works.
:::

::: context void Elements with nothing inside
Most elements wrap something: text, or other elements. A few never can, so they have no closing tag. These are called **void elements**. `img` is one, and you will meet `input` in lesson 5. You may see them written `<img … />`, with a slash before the `>`. That style comes from an older, stricter cousin of HTML called XHTML. Browsers accept it and ignore the slash. Writing `</img>` is a mistake, though; browsers ignore that too.
:::

::: context alt-text Writing alt text that helps
Ask: if this picture vanished, what would the reader miss? Write that, in a short sentence. Leave out "picture of" or "image of": a screen reader already says it is an image. If the picture contains words, such as a logo or a sign, the alt text should contain those words. If the picture is a link, describe where it goes ("Orbit Shop home"), not what it looks like. In many countries, public websites are required by law to be usable by people with disabilities, and missing alt text is one of the most common failures found when they are tested.
:::

::: context pixels What a pixel is
A **pixel**, short for "picture element", is one tiny dot of colour on a screen. A picture is a grid of them, and so is the screen itself. In HTML and CSS, a pixel is a fixed small length, about the size of one dot on an ordinary computer screen. Modern phones pack two or three real dots into each of these "CSS pixels", so sizes look about the same on every device. A width of 200 is roughly the width of a phone screen's left half.
:::

=== web-04 | Lists
--- teach
Last lesson you linked pages together and added pictures. This lesson is about lists: a row of items, one under another. They are everywhere on the web, far more than you might guess.

Think of two lists you might stick on the fridge. A shopping list has bullet points, because the order does not matter: you can buy the milk before the bread. A recipe has numbered steps, because the order matters a lot: you cannot ice the cake before you bake it. HTML has one kind of list for each.

### Bullet lists

A list where the order does not matter is an **unordered list**, written `ul`. Each item in it is a **list item**, written `li`:

```html
<ul>
  <li>Warm socks</li>
  <li>A torch</li>
  <li>Sleeping bag</li>
</ul>
```

Read it from the top:

- `<ul>` opens the list.
- Each `<li>` … `</li>` is one item. The browser puts a bullet point in front of it.
- `</ul>` closes the list.

The items are indented by two spaces. That is only for people reading the code: as you saw in lesson 1, the browser ignores the extra spaces. But the indent makes it easy to see which items belong to which list.

### Numbered lists

A list where the order matters is an **ordered list**, written `ol`. Its items are `li` too:

```html
<ol>
  <li>Boil the water</li>
  <li>Add the pasta</li>
  <li>Drain it after ten minutes</li>
</ol>
```

The browser writes the numbers 1, 2 and 3 for you. You never type them. Add a new step in the middle, and every number after it [[moves up by itself|auto-numbers]].

### Only list items inside a list

A `ul` or an `ol` holds only `li` elements. Put text, a heading or a paragraph inside the `li`, never straight inside the `ul`.

**Watch out:** an `li` must be inside a `ul` or an `ol`. A list item written after `</ul>` has closed is not part of that list. The browser still draws it, so the page can look almost right, but a screen reader no longer counts it as one of the list's items. When a list "has" an item the checks cannot find, see whether it slipped outside the closing tag. Lists [[carry meaning|list-meaning]], not only bullets.

### Starting from another number

An ordered list can start counting from a number other than 1. Give the `ol` a `start` attribute:

```html
<ol start="7">
  <li>Paint the fence</li>
  <li>Clean the brushes</li>
</ol>
```

That list is numbered 7 and 8. It is handy when a list carries on after some text, such as steps 7 and 8 on the second page of instructions.

### A list inside a list

An item can hold a whole list of its own. Put the inner list inside the `li`, after the item's text and before its `</li>`:

```html
<ul>
  <li>Fresh fruit
    <ul>
      <li>Green apples</li>
      <li>Ripe pears</li>
    </ul>
  </li>
  <li>Brown bread</li>
</ul>
```

The outer list has two items, `Fresh fruit` and `Brown bread`. The `Fresh fruit` item holds an inner list with two items of its own. The browser indents the inner list and [[changes its bullet style|nested-bullets]], so you can see the levels.

### Lists of links

A list item can hold any inline element, including a link. A row of links, one per item, is how almost every website builds its **[[menu|menus]]**:

```html
<ul>
  <li><a href="shop.html">Gift shop</a></li>
  <li><a href="help.html">Get help</a></li>
</ul>
```

It looks like a plain bullet list for now. Once you learn CSS, you can line those items up side by side, and it becomes the menu bar across the top of a page.

::: context auto-numbers Why the browser does the counting
If you typed the numbers yourself, every time you added or removed a step you would have to renumber everything after it, by hand, and sooner or later you would get one wrong. Letting the browser count means the numbers are always right. This is a pattern you will see again and again in programming: when a computer can work something out from the data, let it, rather than writing the answer in by hand. Lesson 12 builds whole lists from data in exactly that spirit.
:::

::: context list-meaning What a screen reader says about a list
When a screen reader meets a real list, it says so before reading the items: something like "list, 3 items". Then, as it reads each one, it may say "1 of 3", "2 of 3". That tells a listener how long the list is and where they are in it, which a sighted reader gets from one glance. Text that only *looks* like a list, such as lines that start with a dash, gives them none of that. So whenever something is a list, write it with `ul` or `ol`.
:::

::: context nested-bullets How deep lists look
Browsers give each level of a bullet list a different marker, so you can tell the levels apart. By default the outer list uses a filled dot, called a **disc**, the next level an open **circle**, and deeper levels a small **square**. Each level is also pushed further to the right. You can change all of this with CSS later. Lists nested more than two or three levels deep get hard to read, so real pages rarely go further.
:::

::: context menus Menus are lists

=== web-05 | Forms and buttons
--- teach
Up to now your pages only talk: headings, text, lists, links and pictures. This lesson lets a page ask questions back. You will build boxes people can type into, boxes they can tick, and a button to press.

Think of a paper form at a hotel desk. Each box has a printed word next to it — "Name", "Room" — so you know what to write where. There is a box to tick if you want breakfast, and at the bottom you hand the whole form over. A web form has exactly the same parts.

### A box to type in

A box people can type into is an `input` element. Like `img`, it is a void element: it has no closing tag.

```html
<input type="text">
```

That draws an empty one-line text box. The `type` attribute says what kind of box it is; `text` is the plain kind, for any words.

### Giving each field a label

A box on its own does not say what to type. A `label` element holds the words that name a **field** — one box on the form:

```html
<label>Your town</label>
```

But a label sitting next to a box is not yet joined to it. To join them, give the box an `id`, and give the label a `for` attribute with the same value.

### id and for

An **id** is a name for one single element on the page. No two elements on a page may share an id, the way no two people share a passport number. The label's `for` says which id it belongs to:

```html
<label for="town">Your town</label>
<input id="town" type="text">
```

Read the two lines together: the label is *for* the element whose *id* is `town`. Now the two are joined, and two things change:

- Clicking the words `Your town` puts the typing cursor into the box. That is called giving the box the **focus**: it is the element your keystrokes now go to.
- A [[screen reader|screen-readers-forms]] reads the label aloud when someone lands on the box, so they know what it is for.

**Watch out:** `for` and `id` must match exactly, letter for letter. `for="Town"` does not join to `id="town"`, because capitals count. Nothing on the screen tells you they failed to join, so test it: click the label and see whether the cursor jumps into the box.

### Kinds of field

The `type` attribute changes what kind of field the box is. Some common ones:

- `text`: any words.
- `email`: an email address. The browser can check that it has an `@` in it.
- `password`: the letters are hidden as dots while you type.
- `number`: a number, with small up and down arrows.
- `checkbox`: a small square you tick or untick.

The right type also helps people on phones, as the note on [[field types and keyboards|phone-keyboards]] explains.

```html
<label for="guests">Guests</label>
<input id="guests" type="number">
```

### Example text that disappears

`placeholder` puts grey example text inside an empty box. It vanishes the moment you start typing:

```html
<input id="town" type="text" placeholder="for example, Leeds">
```

The box is still empty: the grey words are only a hint, not something typed into it.

**Watch out:** a placeholder is not a label. It disappears as soon as someone types, so they can no longer see what the box was for. Always give the field a real `label` too.

### Starting filled in

The `value` attribute puts real text into the box when the page opens. Someone can then change it or leave it:

```html
<input id="nights" type="number" value="2">
```

For a checkbox, add the attribute `checked` to make it start ticked. It needs no value at all: being there is enough. That makes it a **[[boolean attribute|boolean-attributes]]**.

```html
<input id="breakfast" type="checkbox" checked>
<label for="breakfast">Breakfast included</label>
```

Clicking the label ticks or unticks the box too, which gives people a much bigger target than the tiny square.

### Buttons and the form around them

A `button` is something people press. Its words go between its tags. A `form` element wraps all the fields that belong together, with the button usually last:

```html
<form>
  <label for="town">Your town</label>
  <input id="town" type="text">
  <button type="submit">Find hotels</button>
</form>
```

`type="submit"` means "this button hands the form in". On a real website that [[sends the answers to a server|submit]].

::: context screen-readers-forms Why the label must be joined
Picture landing on a text box without seeing the page. A screen reader can only say "edit text, blank". You have no idea whether to type your name, your email or your age. With a joined label, it says "Your town, edit text". Joining labels is one of the first things checked when a website is tested for **accessibility**: how well it works for people with disabilities. It also helps everyone else, since clicking a label is easier than hitting a small box, especially a checkbox, on a phone.
:::

::: context phone-keyboards The right keyboard on a phone
On a phone, the `type` of a field changes the on-screen keyboard. An `email` field shows a keyboard with the `@` key and a `.com` key close at hand. A `number` field can show a keypad of digits. A `password` field turns off spelling correction and suggestions, so the phone does not try to remember or "fix" your password. The page works the same on a laptop, but on a phone the right type saves people a lot of fiddling.
:::

::: context boolean-attributes Attributes that are on or off
A **boolean** is a value that can only be true or false, named after the mathematician George Boole, who worked out the rules of true-and-false logic in the 1800s. A boolean attribute such as `checked` works like a light switch: if it is written in the tag, it is on; if it is missing, it is off. Writing `checked="false"` does not turn it off: the attribute is still there, so the box is still ticked. To start unticked, leave `checked` out completely.
:::

::: context submit What submitting really does
On a real site, a submit button sends what was typed to a **server**, a computer that runs the website, which can save it, check a password, or look something up. The form's `action` and `method` attributes say where and how to send it. In these lessons, nothing is ever sent: the preview stops the form from leaving the page. In the next course, you will catch the moment a form is handed in with JavaScript and deal with the answers yourself, right on the page.
:::

=== web-06 | CSS: colour and type
--- teach
For five lessons you have written HTML, which says what each piece of a page *is*: a heading, a list, a form. The browser has drawn everything in its plain default look: black text, white background, one typeface. This lesson starts **CSS**, the language that says how things *look*.

Think of a house. HTML is the walls, doors and rooms. CSS is the paint, the wallpaper and the carpet. You can repaint every room without moving a single wall, and the same walls can look completely different from one house to the next.

### A style element and a rule

The simplest place to write CSS is a `style` element in your page. Inside it you write **rules**. A rule says "these elements should look like this":

```html
<style>
  h2 {
    color: purple;
  }
</style>
```

That one rule makes every `h2` on the page purple. Its parts:

- `h2` is the **selector**: it picks which elements the rule is for. Here, every `h2`.
- The curly brackets `{` and `}`, also called **braces**, hold what to do to them.
- `color: purple;` is a **declaration**: one thing about the look. It has a **property** (`color`, which thing to change), a colon `:`, the **value** (`purple`, what to change it to), and a semicolon `;` to end it.

CSS uses the American spelling `color`, without a u. Writing `colour` does nothing. The name CSS itself [[stands for something|css-name]].

### Three ways to write a colour

`color` sets the colour of the text. You can write the value three ways:

- a **name**: `purple`, `tomato`, `navy`, `gold`, `grey`. There are about 140 names.
- a **[[hex code|hex]]**: a `#` followed by six digits or letters, such as `#800080`.
- an **[[rgb value|rgb]]**: three numbers from 0 to 255 for how much red, green and blue to mix, such as `rgb(128, 0, 128)`.

Those three are the same purple. However you write it, the browser stores it as `rgb(…)`. That is why the checks in these lessons ask for colours as `rgb(…)`.

### The size of text

`font-size` sets how big the text is. The usual unit is `px`, pixels, written straight after the number with no space:

```css
h3 {
  font-size: 30px;
}
```

A rule can hold as many declarations as you like, one per line, each ending with its semicolon.

### The typeface

`font-family` picks the typeface, the shape of the letters. Give a list, separated by commas, and the browser uses the first one the computer has:

```css
p {
  font-family: Verdana, sans-serif;
}
```

The last item should be a general family the browser always has: `serif` (letters with little feet, like a newspaper), `sans-serif` (without), or `monospace` (every letter the same width, like a typewriter). A name with spaces in it goes in quotes: `"Times New Roman"`. The note explains [[why the list is needed|fonts]].

### The background

`background-color` paints the area behind an element:

```css
h3 {
  background-color: lightyellow;
}
```

### One rule for several selectors

To give several kinds of element the same look, list their selectors with commas between them:

```css
h3, h4 {
  color: teal;
}
```

That one rule colours every `h3` and every `h4`.

### Styles pass down to what is inside

Some properties, such as `color`, `font-size` and `font-family`, are **inherited**: an element that does not set them takes them from the element it sits inside. Set them on `body`, and every heading, paragraph and list item inside the body takes them too:

```css
body {
  font-family: Georgia, serif;
}
```

Now the whole page uses Georgia, unless a rule for some element says otherwise. A `strong` inside a paragraph has the paragraph's colour for the same reason. `background-color` is [[not inherited|inheritance]], but the parent's background shows through any child that has none.

### When two rules disagree, the later one wins

What if two rules set the same property on the same element?

```css
h3 {
  color: teal;
  font-size: 30px;
}
h3 {
  color: crimson;
}
```

The `h3` comes out crimson: when two rules of the same kind clash, the one written **later** wins. But only the clashing property is replaced. The first rule's `font-size: 30px` still applies, because nothing later disagrees with it. This is the start of what is called [[the cascade|cascade]].

### Comments in CSS

A CSS comment starts with `/*` and ends with `*/`. The browser skips it:

```css
/* Brand colours, agreed with the design team */
```

**Watch out:** a missing semicolon breaks more than one line. In `color: teal font-size: 30px;` the browser reads everything up to the next semicolon as one value for `color`, finds that `teal font-size: 30px` is not a colour, and throws the whole thing away. Neither the colour nor the size is set. When a style "does nothing", check the line above it for its semicolon.

::: context css-name What CSS stands for
**CSS** stands for **Cascading Style Sheets**. A **style sheet** is an old printing term: a page of rules for how a publication should look, such as which typeface the headlines use. **Cascading** describes how many rules, from many places, flow together into one final look, with clear rules for which one wins. It was proposed by Håkon Wium Lie in 1994, when people were stuffing design into HTML tags and pages were becoming a tangle.
:::

::: context hex How hex codes work
A hex code is three pairs of characters: red, green, blue. Each pair is a number written in **hexadecimal**, counting in sixteens instead of tens, with the digits 0 to 9 and then the letters a to f standing for 10 to 15. So each pair goes from `00`, meaning none, to `ff`, meaning the most, which is 255. `#ff0000` is all red and nothing else. `#000000` is black and `#ffffff` is white. `#808080` is a middle grey: 80 in hexadecimal is 8 sixteens, which is 128.
:::

::: context rgb Mixing light
A screen makes every colour from tiny red, green and blue lights. `rgb(30, 144, 255)` says: red at 30 out of 255, green at 144, blue at 255. Mixing light works differently from mixing paint: all three at full, `rgb(255, 255, 255)`, gives white, and all three off gives black. Red and green together make yellow. The numbers stop at 255 because each one is stored in one **byte**, 8 bits of computer memory, which can hold 256 different values, from 0 to 255.

```svg
<svg xmlns="http://www.w3.org/2000/svg" viewBox="0 0 360 120" font-family="Inter, Arial, sans-serif">
  <rect x="10" y="20" width="100" height="40" fill="#ff0000"/>
  <rect x="130" y="20" width="100" height="40" fill="#00ff00"/>
  <rect x="250" y="20" width="100" height="40" fill="#0000ff"/>
  <text x="60" y="82" font-size="12" text-anchor="middle" fill="#1f2a44">rgb(255, 0, 0)</text>
  <text x="180" y="82" font-size="12" text-anchor="middle" fill="#1f2a44">rgb(0, 255, 0)</text>
  <text x="300" y="82" font-size="12" text-anchor="middle" fill="#1f2a44">rgb(0, 0, 255)</text>
  <text x="180" y="108" font-size="12" text-anchor="middle" fill="#6c7a93">all three at 255 make white; all at 0 make black</text>
</svg>
```
:::

::: context fonts Why a list of typefaces
A page does not carry its typefaces with it unless you tell it to fetch them. It asks the visitor's computer to use one it already has. A typeface you love may simply not be installed on someone else's phone. So you give a list: "Verdana if you have it, otherwise any sans-serif". The browser walks the list and uses the first match. That last general family always works, so the page never falls back to something wildly different. Websites can also download their own typefaces, which the advanced courses cover.
:::

::: context inheritance Which properties pass down
The properties that pass down are mostly about **text**: `color`, `font-size`, `font-family`, `font-weight`, `text-align`. That makes sense: you want a whole article in the same typeface without repeating it for every paragraph. The properties that do not pass down are mostly about the **box**: backgrounds, borders, padding and margins. If borders were inherited, putting one around a list would put one around every item in it too. A few elements, such as links and form buttons, start with their own colour from the browser, so they do not take their parent's colour unless you say so.
:::

::: context cascade The cascade, in brief
The browser gathers every rule that matches an element: its own built-in defaults, your style sheets, and any styles written on the element. Where they clash, it decides in a fixed order. A more **specific** selector wins over a less specific one; you will see that in the next lesson, where a class beats a plain tag name. Only when two rules are equally specific does the later one win. Those two ideas, specificity and order, explain almost every "why is my style not working?" moment in CSS.
:::

=== web-10 | JavaScript: reacting to a click
--- teach
A `<script>` tag runs JavaScript in the page. It can find elements and change them — that is the **DOM** (the page as objects):

```html
<button id="launch">Launch</button>
<p id="status">Waiting</p>

<script>
  const button = document.querySelector('#launch')
  const status = document.querySelector('#status')

  button.addEventListener('click', () => {
    status.textContent = 'Lift off!'
  })
</script>
```

`querySelector` takes the same selectors as CSS. `addEventListener('click', …)` runs a function every time the button is clicked. Put the script after the elements it uses.

The JavaScript in that example, piece by piece:

- `const button = …` makes a **variable**: a name for a value, here the element found on the page. Use `const` for a name that will always mean the same thing, and `let` for one you will change later: `let n = 0`, then `n = n + 1`.
- `() => { … }` is an **arrow function**: a block of code saved to run later. Handing it to `addEventListener` means "run this every time the button is clicked", not "run it now".
- `'Lift off!'` is a **string** — text in quotes, single or double.

=== web-12 | Building a list from data
--- teach
Pages are usually built from data. Loop over an array and create an element for each item:

```html
<ul id="crew"></ul>

<script>
  const crew = ['Ada', 'Lin', 'Sam']
  const list = document.querySelector('#crew')

  for (const name of crew) {
    const li = document.createElement('li')
    li.textContent = name
    list.appendChild(li)
  }
</script>
```

`['Ada', 'Lin', 'Sam']` is an **array**: several values in order, inside square brackets. `for (const name of crew) { … }` is a **`for…of` loop**: it runs the block once for each item, with `name` holding the current one — `'Ada'`, then `'Lin'`, then `'Sam'`.

`createElement` makes a new element, `textContent` fills it, and `appendChild` puts it on the page. This is, underneath, what every front-end framework does.
