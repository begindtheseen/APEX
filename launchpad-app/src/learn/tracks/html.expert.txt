=== web4-01 | A store: dispatch, reducers and subscribe
--- teach
The advanced course kept pages correct with one state object and one `render()`. This course scales that up: stores, derived data, keyed rendering, undo, reusable elements, performance, accessibility audits, focus and routing.

As an app grows, "handlers change state and call render" needs one more rule: **all changes go through one door.** That door is a **store**, and the flow is always one way:

```
event  →  dispatch(action)  →  reducer(state, action)  →  new state  →  subscribers (render, log, save…)
```

- An **action** is a plain object describing what happened: `{ type: 'increment' }`, `{ type: 'setStep', step: 5 }`.
- A **reducer** is a *pure* function `(state, action) => newState`. It never changes the old state; it returns a new object (`{ ...state, count: state.count + 1 }`). Same inputs, same output, no side effects.
- **Subscribers** are functions the store calls after every change. `render` is one; a logger is another. `subscribe` returns a function that unsubscribes.

```js
function createStore(reducer, initialState) {
  let state = initialState
  const listeners = new Set()
  return {
    getState: () => state,
    dispatch(action) {
      state = reducer(state, action)
      for (const listener of listeners) listener(state, action)
    },
    subscribe(listener) {
      listeners.add(listener)
      return () => listeners.delete(listener)
    },
  }
}
```

Some JavaScript in it: `new Set()` is a collection that holds each value once (`add`, `delete`, and `for…of` to loop over it); `dispatch(action) { … }` inside an object literal is shorthand for a method; and `state` and `listeners` live on inside the returned functions, a closure. Your reducer can use `switch (action.type)`, which runs the `case` whose value matches and `default` when none does.

Why pure reducers matter: because every change produces a *new* object, anything that kept an old state still has the old values. That is what makes undo, time-travel debugging and cheap "did anything change?" checks (`prev === next`) possible. A reducer that mutates (`state.count += 1; return state`) breaks all of that silently — every saved "old" state is the same object as the new one.

This is the design of Redux, and of React's `useReducer`; Vue and Svelte stores are close cousins.

=== web4-02 | Design: derive it, don't store it
--- teach
A state object tends to collect copies: the list of items, *and* how many are done, *and* the filtered list the page shows. Each copy is another thing every handler must keep in sync, and sooner or later one handler forgets. That is not carelessness; it is a design that makes the mistake easy.

**Store the minimum. Derive the rest.** If a value can be computed from other state, compute it when you need it:

```js
const state = { items: [...], filter: 'all' }   // the facts, nothing else

function countDone(items) {
  return items.filter((item) => item.done).length
}
function visibleItems(state) {
  if (state.filter === 'open') return state.items.filter((i) => !i.done)
  if (state.filter === 'finished') return state.items.filter((i) => i.done)
  return state.items
}

function render() {
  const shown = visibleItems(state)
  // … draw `shown`, and `${countDone(state.items)} of ${state.items.length} done`
}
```

These little functions are called **selectors**: they take state and answer a question about it. They can't go stale, because they are recomputed from the facts every time. Handlers get simpler too — toggling an item just flips `done`; nothing else needs remembering.

"Isn't recomputing wasteful?" Filtering a few hundred items takes microseconds. If a selector ever does become expensive, you *memoize* it (cache the answer until its inputs change) — but you start from derived values and optimise later, never the other way round.

A quick test for any piece of state: *could I compute this from the rest?* If yes, it is not state.
--- task

=== web4-03 | Keyed rendering: update, don't rebuild
--- teach
Rebuilding a list from scratch on every change is simple, and it has a cost you only notice when the elements hold something of their own: text half-typed into an input, keyboard focus, a scroll position, a running animation, an open `<details>`. Throw the element away and all of that goes with it.

**Keyed rendering** keeps each data item's element for as long as the item exists. Give every item a stable **key** (its id — never its position, which changes when items move), remember which element belongs to which key, and on each render:

1. **Create** an element for a key you haven't seen.
2. **Update** the existing element for a key you have — change only what differs, like its label's text.
3. **Move** elements into the right order.
4. **Remove** elements whose keys are gone.

```js
const rows = new Map()   // key → element

function render() {
  const seen = new Set()
  items.forEach((item, index) => {
    let li = rows.get(item.id)
    if (!li) {
      li = createRow(item)
      rows.set(item.id, li)
    }
    li.querySelector('.label').textContent = item.label     // update in place
    const here = list.children[index]
    if (here !== li) list.insertBefore(li, here || null)    // move only if needed
    seen.add(item.id)
  })
  for (const [id, li] of rows) {
    if (!seen.has(id)) {
      li.remove()
      rows.delete(id)
    }
  }
}
```

`new Map()` is a dictionary whose keys can be anything, numeric ids included: `get`, `set`, `has`, `delete`, and `for (const [key, value] of map)` to loop. `insertBefore` *moves* an element that is already in the page; it doesn't copy it. This, give or take, is what React's `key` prop and Vue's `:key` are for: they tell the framework which element is which, so it can reconcile instead of rebuild. Using the array index as a key reintroduces the bug the moment the list is reordered.

=== web4-04 | Undo and redo
--- teach
Undo looks like a feature; it is really a data structure. Keep three things:

```js
const history = {
  past: [],          // states before this one, oldest first
  present: '#ffffff',
  future: [],        // states you have undone, next one first
}
```

- **A change**: push `present` onto `past`, set the new `present`, and **empty `future`**. (Once you do something new, the undone branch is gone — that is how every editor behaves.)
- **Undo**: if `past` is empty, do nothing. Otherwise put `present` at the front of `future`, and pop the last of `past` into `present`.
- **Redo**: the mirror image — push `present` onto `past`, and take the first of `future`.

```js
function undo() {
  if (!history.past.length) return
  history.future.unshift(history.present)
  history.present = history.past.pop()
  render()
}
```

This only works because each state is a *value* that doesn't change after it is saved — the purity lesson from the store paying off. With objects, save new objects (`{ ...old, color }`); never mutate one that is already in `past`.

Two details that separate a good undo from a sloppy one:

- **Don't record non-changes.** Choosing the colour that is already chosen shouldn't create an undo step that appears to do nothing.

=== web4-05 | Templates and cloning
--- teach
Building markup from strings — `` li.innerHTML = `<h3>${launch.name}</h3>…` `` — is quick to write and has two real problems. Any data containing `<` is parsed as HTML (a name like `Starliner <Crew Flight Test>` loses its second half, and worse inputs run code). And the markup is buried inside JavaScript where nobody styling the page will find it.

The `<template>` element holds markup that the browser parses but **doesn't render**. Its `content` is a `DocumentFragment` — a lightweight holder for nodes that isn't part of the page — which you **clone** for each item, fill with `textContent`, and insert:

```html
<template id="row-template">
  <li class="row">
    <span class="row__name"></span>
    <button class="row__remove" type="button">Remove</button>
  </li>
</template>
```

```js
const template = document.querySelector('#row-template')

function Row(item) {
  const li = template.content.firstElementChild.cloneNode(true)   // true: deep, with children
  li.dataset.id = item.id
  li.querySelector('.row__name').textContent = item.name
  return li
}

list.append(...items.map(Row))
```

`cloneNode(true)` copies the element and everything inside it; it is fast, because the browser only parsed the template once. Cloning `template.content` itself gives you a fragment (inserting it moves its children into the page, leaving the fragment empty); cloning `firstElementChild` gives you the element directly, which is handier when you want to keep a reference to it.

The markup is now HTML where it belongs, data only ever goes in as text, and each row is still a component: data in, element out.

=== web4-06 | Custom elements
--- teach
**Custom elements** let you add your own tags to HTML. Once defined, `<star-rating value="3"></star-rating>` works anywhere — in plain HTML, from `innerHTML`, inside a React or Vue app — because the browser itself knows what it is.

```js
class StarRating extends HTMLElement {
  static observedAttributes = ['value', 'max']

  connectedCallback() {            // added to the page
    this.render()
  }
  attributeChangedCallback() {     // an observed attribute changed
    if (this.isConnected) this.render()
  }
  get value() {
    return Number(this.getAttribute('value') || 0)
  }
  set value(v) {
    this.setAttribute('value', v)  // reflect the property to the attribute
  }
  render() { /* build the stars from this.value and this.max */ }
}

customElements.define('star-rating', StarRating)   // the name must contain a hyphen
```

The lifecycle: the **constructor** runs when the element is created (don't touch attributes or children there); `connectedCallback` when it enters the page; `attributeChangedCallback(name, oldValue, newValue)` whenever an attribute listed in `observedAttributes` changes — from HTML, from `setAttribute`, from anyone.

Three class features appear here: `extends HTMLElement` makes the class a kind of element, so a constructor must call `super()` before anything else; `static observedAttributes` belongs to the class itself rather than to each element; and `get value()` / `set value(v)` make reading or assigning `el.value` run your code.

**Attributes are the element's public API.** Make the attribute the source of truth: a click sets `value`, which sets the attribute, which triggers `attributeChangedCallback`, which re-renders. Then outside code changing the attribute works exactly like a click.

**Tell the outside world** with an event: `this.dispatchEvent(new CustomEvent('change', { detail: { value }, bubbles: true }))`. The page listens for it the same way it would on an `<input>`.

A custom element can also attach a **shadow root** to hide its insides and scope its CSS. Here you will render into the element's ordinary children ("light DOM"), which keeps it simple and styleable from the page.

=== web4-07 | Performance: batching and debouncing
--- teach
Two habits prevent most front-end slowness.

**1. Batch DOM changes.** Every insertion into the live page is work the browser may have to account for — styles, layout, observers, accessibility tree. Appending 1,000 rows one at a time means 1,000 separate changes. Build them off-page first and insert once:

```js
const fragment = document.createDocumentFragment()
for (const ship of ships) {
  const li = document.createElement('li')
  li.textContent = ship
  fragment.append(li)          // off the page: cheap
}
list.append(fragment)          // one change to the page
```

A `DocumentFragment` is a container that vanishes when inserted: its children move into the page in a single operation. To *replace* a list's contents in one operation, `list.replaceChildren(fragment)` removes the old children and inserts the new ones as one change. Worse than many insertions is **layout thrashing**: alternating writes (`el.style.width = …`) with reads that need layout (`el.offsetHeight`) inside a loop, forcing the browser to recalculate on every read. Do all your reads, then all your writes.

**2. Debounce bursts of events.** An `input` event fires on every keystroke. If each one filters a big list (or calls a server), typing "falcon" does the work six times and only the last one matters. A **debounced** function waits until the events stop for a moment:

```js
function debounce(fn, ms) {
  let timer = null
  return (...args) => {
    clearTimeout(timer)                             // a new event cancels the pending call
    timer = setTimeout(() => fn(...args), ms)
  }
}

input.addEventListener('input', debounce(applyFilter, 250))
```

Each event restarts the countdown; `applyFilter` runs once, 250ms after the last keystroke. (Its cousin, **throttling**, runs at most once per interval — better for scroll and resize.)

The first script on this lesson's page is a meter: it counts the changes made to the list and how often the filter really runs.

=== web4-08 | Debugging: results for the wrong search
--- teach
Some bugs only exist in time. Two requests go out; they come back in the other order; the older answer overwrites the newer. On a fast connection you never see it. On a train, the search box shows results for what you typed a second ago. It's called a **race condition**, and every UI that fetches while the user types has to handle it.

**Reproduce it deliberately.** Races hide when things are fast, so make them slow: add artificial delays, or use the browser's network throttling. Here the fake server answers short queries *slower* than long ones, which is realistic — broad queries have more results to gather.

**Draw the timeline.** Type `m`, then `ma`:

```
0ms    request "m"   sent  ─────────────────────────┐ (250ms)
10ms   request "ma"  sent  ────────┐ (100ms)         │
110ms                    "ma" arrives → shows ma ✓   │
250ms                                  "m" arrives → shows m ✗
```

The code awaited each answer and rendered it, trusting that answers arrive in order. They don't.

**Fix the cause: only the latest request may render.** Number each request; when an answer arrives, check it is still the newest:

```js
let latest = 0

input.addEventListener('input', async () => {
  const id = ++latest
  const results = await search(input.value)
  if (id !== latest) return          // a newer search has started: ignore this answer
  render(results)
})
```

With real `fetch`, an `AbortController` goes further and cancels the stale request. Either way the rule is the same: *the UI shows the answer to the question currently being asked.* Debouncing makes the race rarer; it doesn't remove it.

=== web4-09 | Design: CSS architecture with tokens and BEM
--- teach
CSS has no modules and one global namespace, so a stylesheet's structure decides whether it stays changeable. Three conventions keep large projects sane.

**1. Design tokens.** Every colour, space and radius is a custom property on `:root`, named for its *role*, not its value:

```css
:root {
  --color-surface: #ffffff;
  --color-text: #1e3a8a;
  --color-primary: #1e90ff;
  --space-4: 16px;
  --radius: 8px;
}
```

**2. Themes swap tokens, not rules.** A dark theme is just new values under an attribute on `html`; no component rule changes:

```css
[data-theme="dark"] {
  --color-surface: #1f2937;
  --color-text: #f9fafb;
}
```

**3. BEM naming.** *Block, Element, Modifier*: `.card` (a standalone component), `.card__title` (a part of it, two underscores), `.card--featured` (a variant, two hyphens). Every selector is a single class:

```css
.card          { background: var(--color-surface); padding: var(--space-4); }
.card__title   { color: var(--color-text); }
.card--featured { border-color: var(--color-primary); }
```

Why single classes? **Specificity stays flat** — every rule scores (0,1,0), so the order you write them in decides, and you never need `!important` or an id to win a fight. Components stop depending on where they sit (`#app div.box h3` breaks the moment someone moves the box). And a class name tells you exactly where its CSS lives.

The smells to remove: id selectors in CSS, long descendant chains, `!important`, the same hex code pasted in ten places, and "dark mode" written as a second copy of every rule.
--- task

- tokens on `:root`: `--color-surface` `#ffffff`, `--color-text` `#1e3a8a`, `--color-primary` `#1e90ff`, `--color-border` `#dddddd`; `[data-theme="dark"]` sets `--color-surface` `#1f2937`, `--color-text` `#f9fafb`, `--color-border` `#374151`
- BEM classes: each box becomes `.card` with a `.card__title` and `.card__body`; the special one also has `.card--featured` (its border uses the primary colour); buttons become `.button` plus `.button--primary` or `.button--secondary`
- `#theme` toggles `data-theme="dark"` on the `html` element (and back)
- no id selectors in the CSS and no `!important`

=== web4-10 | Debugging: an accessibility audit
--- teach
An accessibility audit is debugging with a checklist. Automated tools (the browser's Lighthouse panel, axe) catch perhaps a third of problems; the rest need a person with a keyboard and a screen reader. A sound order to work in:

1. **Structure.** Is the page's language set (`<html lang="en">`), so a screen reader pronounces it correctly? Is there one `h1`, with headings in order? Are there landmarks?
2. **Images.** Every `img` has an `alt` — descriptive, or empty if decorative.
3. **Forms.** Every field has a real `label`. Placeholders vanish when typing starts and are often too faint to read.
4. **Controls.** Everything clickable is a `button` or a link, reachable and pressable by keyboard. Icon-only buttons need an accessible name: `aria-label="Menu"`.
5. **Focus.** Can you *see* where focus is? `outline: none` with no replacement leaves keyboard users lost. And **positive `tabindex`** (`tabindex="3"`) rips the element out of the natural order — use `0` (join the natural order) or `-1` (focusable by script only), never a positive number.
6. **Contrast.** Body text needs a contrast ratio of at least **4.5 : 1** against its background (WCAG AA). Light grey `#bbbbbb` on white is about 1.9 : 1 — unreadable for many people, and in sunlight for everyone. `#595959` on white is about 7 : 1.

Each finding gets fixed at its cause. Resist the quick patches: `role="button"` on a `div` announces a button that still can't be pressed; `aria-label` on an input *can* name it, but a visible `label` helps everyone, including sighted users.

=== web4-11 | Focus management
--- teach
When the page changes under the keyboard focus, *you* decide where focus goes. If you don't, the browser does — and its answer is usually "nowhere".

Delete an item by pressing its Remove button, and that button is gone. Focus falls back to the `body`; the next Tab starts again from the top of the page. For a keyboard or screen reader user, every deletion means finding their place again. The rules of thumb:

- **After removing an item**, focus the equivalent control on the item that took its place (the next one), or the previous one if it was the last, or — when the list is empty — a sensible landmark such as the list's heading.
- **After opening something** (a panel, a dialog), focus its first useful control. **After closing**, return focus to what opened it.
- **Announce changes that aren't visible where focus is**, using a live region: an element with `aria-live="polite"` whose text changes is read out when the reader is idle.

A heading isn't normally focusable; `tabindex="-1"` makes it focusable by script (`heading.focus()`) without adding it to the Tab order.

```js
function removeAt(index) {
  const [gone] = crew.splice(index, 1)
  render()
  const buttons = list.querySelectorAll('.remove')
  const target = buttons[index] || buttons[index - 1] || heading
  target.focus()
  announce.textContent = `Removed ${gone}`
}
```

`crew.splice(index, 1)` removes one item at `index` and returns an array of what it removed; `const [gone] = …` takes that array's first item.

Note the order: change state, render, **then** find the element to focus in the freshly rendered page — elements from before the render may no longer exist.

Accessible names matter here too: five buttons all named "Remove" are indistinguishable in a screen reader's list of controls. `aria-label="Remove Ada"` fixes that.
--- task

- each `.remove` button's accessible name is `Remove <name>` (via `aria-label`)

- `#announce` (a polite live region) says `Removed <name>`

=== web4-12 | A router on location.hash
--- teach
A single-page app shows different "pages" without loading new documents, and still needs real addresses: something to bookmark, share, and go Back to. The simplest router uses the part of the URL after `#` — the **hash** — because changing it never reloads the page:

```js
location.hash = '#/planets/mars'                      // changes the address, no reload
window.addEventListener('hashchange', route)          // fires after every change, Back included
```

A router is a function from the current address to a view:

```js
function route() {
  const path = location.hash.slice(1) || '/'          // '#/planets/mars' → '/planets/mars'
  const parts = path.split('/').filter(Boolean)       // ['planets', 'mars']
  if (path === '/') return showHome()
  if (parts[0] === 'planets' && parts.length === 1) return showPlanets()
  if (parts[0] === 'planets' && parts.length === 2) return showPlanet(parts[1])   // a route parameter
  showNotFound()
}
route()   // and once at start, for whatever address the page opened on
```

Every view, including **Not found**, is just rendering. Mark the current section's nav link with `aria-current="page"`, so screen readers announce "current page".

**Links.** Normally `<a href="#/about">` changes the hash by itself. This preview page is special: it is an `about:srcdoc` document whose relative links resolve against the *app's* address, so a plain click would load a different page into the frame. So the router **intercepts link clicks** — one delegated listener that cancels the default and sets `location.hash` itself:

```js
document.addEventListener('click', (event) => {
  const link = event.target.closest('a[href^="#/"]')
  if (!link) return
  event.preventDefault()
  location.hash = link.getAttribute('href')
})
```

That is also exactly what real routers do in the modern variant, with `history.pushState` and clean paths instead of hashes. Note that `hashchange` fires a moment *after* the hash changes, not during the click.

- the nav link for the current section gets `aria-current="page"` (the Planets link for any planets page); the others have none

=== web4-13 | A form wizard as a state machine
--- teach
A multi-step form tends to grow booleans — `isOnStep2`, `showBack`, `submitted`, `canContinue` — that can combine into states that should be impossible: on step 3 and submitted and showing Back. A **finite state machine** makes the impossible unrepresentable. Name the states, and list which **events** move from each to which:

```js
const machine = {
  details: { NEXT: 'address' },
  address: { BACK: 'details', NEXT: 'review' },
  review:  { BACK: 'address', SUBMIT: 'done' },
  done:    {},
}
let current = 'details'

function send(event) {
  const next = machine[current][event]
  if (!next) return                    // not allowed from here: ignore it
  current = next
  render()
}
```

Now there is exactly one variable for "where are we", and anything not in the table simply cannot happen: you can't SUBMIT from `details`, and nothing leaves `done`.

**Guards** are conditions on a transition: NEXT from `details` only if a name was entered. Check them in `send` before moving, and show why when they fail.

**Keep the form's data separate from the machine's state.** The answers live in their own object (or in the inputs, which stay in the page when their step is hidden). Going Back must not lose what was typed.

`render()` then derives everything from `current`: which step is visible, which buttons show, what the progress line says. There is no way for the buttons and the visible step to disagree, because both come from one value.

Libraries like XState build on exactly this idea; for most UIs, the table and a `send` function are enough.
--- task

- only the current step's section is visible; `#progress` says `Step 1 of 3` … `Step 3 of 3`, then `Finished`
- `#back` is hidden on `details` and `done`; `#next` is hidden on `review` and `done`; `#submit` is visible only on `review`
- NEXT from `details` needs a name (else `#error` says `Please enter your name.`), from `address` a city (`Please enter your city.`); `#error` is empty otherwise
- `#summary` on the review step says like `Ada from Lisbon`; on `done`, `#thanks` says `Welcome aboard, Ada!`
- going back keeps what was typed

<script>
  const nameInput = document.querySelector('#name')
  const cityInput = document.querySelector('#city')

  const machine = {
    details: { NEXT: 'address' },
    address: { BACK: 'details', NEXT: 'review' },
    review: { BACK: 'address', SUBMIT: 'done' },
    done: {},
  }
  const steps = ['details', 'address', 'review']
  const guards = {
    details: () => (nameInput.value.trim() ? '' : 'Please enter your name.'),
    address: () => (cityInput.value.trim() ? '' : 'Please enter your city.'),
  }
  let current = 'details'
  let error = ''

  function send(event) {
    const next = machine[current][event]
    if (!next) return
    if (event === 'NEXT' && guards[current]) {
      error = guards[current]()
      if (error) return render()
    }
    error = ''
    current = next
    render()
  }

  function render() {
    for (const step of [...steps, 'done']) {
      document.querySelector(`#step-${step}`).hidden = step !== current
    }
    document.querySelector('#progress').textContent = current === 'done' ? 'Finished' : `Step ${steps.indexOf(current) + 1} of 3`
    document.querySelector('#back').hidden = !machine[current].BACK
    document.querySelector('#next').hidden = !machine[current].NEXT
    document.querySelector('#submit').hidden = !machine[current].SUBMIT
    document.querySelector('#error').textContent = error
    const name = nameInput.value.trim()
    document.querySelector('#summary').textContent = `${name} from ${cityInput.value.trim()}`
    document.querySelector('#thanks').textContent = `Welcome aboard, ${name}!`
  }

  document.querySelector('#back').addEventListener('click', () => send('BACK'))
  document.querySelector('#next').addEventListener('click', () => send('NEXT'))
  document.querySelector('#submit').addEventListener('click', () => send('SUBMIT'))

  render()
</script>

=== web4-14 | Problem finding: four bugs, one report
--- teach
Real bug reports arrive in bundles, written by someone describing symptoms, not causes. Handling one well is a skill of its own:

1. **Split it.** Number each symptom and treat it as its own bug. Two symptoms may share a cause, or one sentence may hide two causes — you find out by reproducing each separately.
2. **Reproduce each one exactly.** Do what the reporter did, step by step, and confirm you see what they saw. If you can't reproduce it, you can't know you've fixed it.
3. **Form a hypothesis, then test it.** "The total is built from strings" is a guess until a `console.log(typeof expense.amount)` proves it. Log the values at the moment things go wrong; don't reason from what the code *should* do.
4. **Fix the cause, at the source.** If amounts are strings, convert them where they enter the program (`Number(input.value)`), not everywhere they are added up.
5. **Re-test everything** — each fix can break another path — and look for the bug's siblings: if the delete handler trusts a position in a filtered list, does anything else?

Common causes worth checking first in front-end code: values from inputs are **always strings**; **indexes** into a filtered or sorted view don't match the underlying array (use ids); **special cases** such as an "All" option that the code treats like any other value; and **missing validation** at the edge where user input enters.
