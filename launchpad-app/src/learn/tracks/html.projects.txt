=== webp-01 | To-do app, part 1: adding tasks
--- teach
This course puts the three Web courses to work: three apps built step by step — a to-do list, a quiz and a shopping cart — then three capstones you design yourself from a specification.

Over the next four lessons you will build a complete to-do app. Each lesson's starter is the previous lesson's solution, so the app grows the way real ones do: a feature at a time, without breaking what already works.

Start every app by deciding its **state** — the facts it has to remember. For a to-do list:

```js
const state = {
  todos: [],     // { id: 1, text: 'Buy fuel', done: false }
  nextId: 1,     // ids are never reused, even after a delete
}
```

Why give every task an id? Because later you will delete, tick off and filter tasks, and you need a way to say *which* task that isn't its position in a list that keeps changing.

Then the loop you know: a `render()` that draws everything from `state`, and handlers that change `state` and call `render()`. The form's `submit` event gives you the Add button and the Enter key in one listener:

```js
form.addEventListener('submit', (event) => {
  event.preventDefault()
  const text = input.value.trim()
  if (!text) return
  state.todos.push({ id: state.nextId++, text, done: false })
  input.value = ''
  render()
})
```

The "items left" line is computed inside `render()` from the todos — never kept as a separate number.
--- task
Make the form add tasks:

- keep the tasks in `state.todos` as objects with an `id`, `text` and `done: false`
- `render()` draws one `li` per task into `#todos`, with `data-id` set to its id and the text in a `span` with the class `text`
- submitting the form (button or Enter) adds the trimmed text, ignores an empty field, and clears the field
- `#left` shows how many tasks are not done: `1 item left`, `2 items left`

=== webp-02 | To-do app, part 2: completing and deleting
--- teach
Each task now needs two controls: a checkbox to tick it off and a button to delete it. Two decisions make this clean.

**Listen once, on the list.** Tasks come and go, so per-item listeners would need re-attaching after every render. One delegated listener on `#todos` handles every item, now and later. A checkbox fires `change` when ticked; a button fires `click`. Both bubble.

```js
list.addEventListener('change', (event) => {
  if (!event.target.matches('.toggle')) return
  const id = Number(event.target.closest('li').dataset.id)
  state.todos.find((todo) => todo.id === id).done = event.target.checked
  render()
})
```

`dataset` values are always strings, so `Number(...)` before comparing with the numeric id.

**Name the controls for assistive technology.** Ten checkboxes and ten buttons all called "Delete" are indistinguishable in a screen reader's list of controls. Give each a name that includes its task:

```js
toggle.setAttribute('aria-label', `Done: ${todo.text}`)
del.setAttribute('aria-label', `Delete ${todo.text}`)
```

And draw the task's state from the data: the checkbox's `checked` and the `li`'s `done` class both come from `todo.done` — never from what the page looked like before.
--- task
Give each task a checkbox and a delete button:

- in each `li`: an `input type="checkbox"` with the class `toggle` (checked when done, `aria-label` like `Done: Buy fuel`), the `.text` span, and a `button` with the class `delete` saying `Delete` (`aria-label` like `Delete Buy fuel`)
- a done task's `li` has the class `done`
- ticking or unticking updates the task; Delete removes it; `#left` stays right

=== webp-03 | To-do app, part 3: filters
--- teach
Filters are the moment many apps go wrong, by keeping a second, filtered copy of the list in state that then drifts out of step with the real one. You already know the fix: the filter is a small piece of state (`'all'`, `'active'` or `'completed'`), and the visible list is **derived** from it every render.

```js
function visibleTodos() {
  if (state.filter === 'active') return state.todos.filter((t) => !t.done)
  if (state.filter === 'completed') return state.todos.filter((t) => t.done)
  return state.todos
}
```

`render()` draws `visibleTodos()`, but "items left" still counts *all* tasks — the filter changes what you see, not what exists.

Filter buttons are **toggle buttons**: `aria-pressed="true"` on the chosen one tells a screen reader which filter is on, and makes a handy styling hook (`[aria-pressed="true"] { font-weight: bold }`).

A filtered view can be empty even when tasks exist ("no completed tasks yet"). An empty message beats a blank space: show `#empty` only when the visible list has nothing in it.

Notice what you *don't* have to do: ticking a task while the Active filter is on makes it disappear from the view automatically, because the next render derives the view again.
--- task
Add filters:

- add three buttons after the form (outside it): `#filter-all` (`All`), `#filter-active` (`Active`) and `#filter-completed` (`Completed`); the chosen one has `aria-pressed="true"`, the others `false`; All is chosen at the start
- the list shows only the matching tasks; `#left` still counts every task that isn't done
- add `<p id="empty" hidden>Nothing here.</p>` after the list, visible only when the filtered list is empty

  const list = document.querySelector('#todos')
  const input = document.querySelector('#todo-text')
  const state = { todos: [], nextId: 1, filter: 'all' }
  const FILTERS = ['all', 'active', 'completed']

  function todoItem(todo) {
    const li = document.createElement('li')
    li.dataset.id = todo.id
    li.classList.toggle('done', todo.done)
    const toggle = document.createElement('input')
    toggle.type = 'checkbox'
    toggle.className = 'toggle'
    toggle.checked = todo.done
    toggle.setAttribute('aria-label', `Done: ${todo.text}`)
    const text = document.createElement('span')
    text.className = 'text'
    text.textContent = todo.text
    const del = document.createElement('button')
    del.type = 'button'
    del.className = 'delete'
    del.textContent = 'Delete'
    del.setAttribute('aria-label', `Delete ${todo.text}`)
    li.append(toggle, ' ', text, ' ', del)
    return li
  }

  function visibleTodos() {
    if (state.filter === 'active') return state.todos.filter((todo) => !todo.done)
    if (state.filter === 'completed') return state.todos.filter((todo) => todo.done)
    return state.todos
  }

  function render() {
    const visible = visibleTodos()
    list.replaceChildren(...visible.map(todoItem))
    document.querySelector('#empty').hidden = visible.length > 0
    const left = state.todos.filter((todo) => !todo.done).length
    document.querySelector('#left').textContent = `${left} ${left === 1 ? 'item' : 'items'} left`
    for (const f of FILTERS) {
      document.querySelector(`#filter-${f}`).setAttribute('aria-pressed', String(state.filter === f))
    }
  }

  const idOf = (el) => Number(el.closest('li').dataset.id)

  document.querySelector('#new-todo').addEventListener('submit', (event) => {
    event.preventDefault()
    const text = input.value.trim()
    if (!text) return
    state.todos.push({ id: state.nextId++, text, done: false })
    input.value = ''
    render()
  })

  list.addEventListener('change', (event) => {
    if (!event.target.matches('.toggle')) return
    state.todos.find((todo) => todo.id === idOf(event.target)).done = event.target.checked
    render()
  })

  list.addEventListener('click', (event) => {
    const del = event.target.closest('.delete')
    if (!del) return
    state.todos = state.todos.filter((todo) => todo.id !== idOf(del))
    render()
  })

  for (const f of FILTERS) {
    document.querySelector(`#filter-${f}`).addEventListener('click', () => {
      state.filter = f
      render()
    })
  }

  render()
</script>

=== webp-04 | To-do app, part 4: bulk actions
--- teach
The last features act on many tasks at once: **Clear completed** and **Toggle all**. With state and render in place, a bulk action is a small function over `state.todos` followed by `render()`:

```js
function clearCompleted() {
  state.todos = state.todos.filter((todo) => !todo.done)
  render()
}
```

**Toggle all** needs one decision: what does it do when some tasks are done and some aren't? The convention: if every task is already done, un-tick them all; otherwise tick them all. `every` answers the question directly:

```js
const allDone = state.todos.length > 0 && state.todos.every((todo) => todo.done)
for (const todo of state.todos) todo.done = !allDone
```

(Check the empty case: `[].every(...)` is `true`, which is why the length test is there. Its partner `some` is true when at least one item passes.)

**Controls that can't do anything shouldn't be offered.** Clear completed with nothing completed is a button that does nothing when pressed. Hide it (`hidden`) until at least one task is done. That decision lives in `render()` too, derived from the todos like everything else.

Take a moment when you finish to look at the whole program. Every feature added in this project touched three places — state, `render()` and one handler — and none of them had to know about the others. That is the payoff of the structure you have been practising.
--- task
Finish the app:

- add `#toggle-all` (`Toggle all`): if every task is done, un-tick them all; otherwise tick them all
- add `#clear-completed` (`Clear completed`): removes every done task; it is hidden (`hidden` attribute) whenever no task is done

=== webp-06 | Quiz app, part 2: answering and scoring
--- teach
Now choices do something. The question is what to remember. Tempting: `score` as a number you add to. Better: remember **which choice the player picked for each question**, and derive the score:

```js
const state = { index: 0, answers: [] }   // answers[2] === 0 means "for question 3, the player chose choice 0"

const score = () => state.answers.filter((chosen, i) => chosen === questions[i].answer).length
```

That one decision makes everything else easy. Whether the current question has been answered is `state.answers[state.index] !== undefined`. What to highlight, what feedback to show, whether Next is allowed — all derive from it. And the results screen in the next part can list the player's mistakes, because the answers are still there.

Once answered, a question is **locked**: disable the choice buttons so a second click can't change the answer. Show the outcome in two ways: colour (classes `correct` and `wrong`) and text (`Correct!`, or which answer was right). Never rely on colour alone — some people can't tell red from green, and screen readers don't announce colours. Putting the feedback in a `role="status"` element gets it read out.

With the handler written as "record the answer, render", there is no way for the score, the highlights and the feedback to disagree.

=== webp-07 | Quiz app, part 3: the results screen
--- teach

```js
const finished = () => state.index === questions.length
```

- the final line, `You scored 3 out of 4`

Build the review from the data you have been keeping all along — this is the moment the decision in part 2 to store every answer (not just a running score) pays for itself.

Small touches matter at the end of a flow: the Next button on the last question should say where it goes (`See results`), rather than a generic "Next" that seems to lead nowhere.

**Restart** is the test of your state design. If the whole quiz is `{ index, answers }`, restarting is two assignments and a render:

```js
state.index = 0
state.answers = []
render()
```

If restarting feels hard — "I have to reset this flag, and clear that list, and re-enable those buttons" — the state has leaked into the page. Here it hasn't: `render()` redraws every button from the state, so there is nothing else to reset.

**The best score** is state that deliberately *survives* a restart, so it sits beside the per-round state rather than inside it (`state.best`, starting `null`). The subtle part is *when* to update it. Not inside `render()`: rendering should only ever read state, never change it, or drawing the page twice could change what it shows.
```js
nextButton.addEventListener('click', () => {
  state.index += 1
  if (finished()) state.best = Math.max(state.best ?? 0, score())
  render()
})
```

`??` gives `0` when `best` is still `null`. Keep your event handlers as the only places that change state, and `render()` as the only place that changes the page.

=== webp-09 | Shopping cart, part 1: products and money
--- teach
The third project is a shop: products, a cart, totals with a discount and shipping, and a checkout. It is mostly arithmetic, which makes it a good place to learn the one rule about money in code:

**Never use floating-point numbers for money.** JavaScript's numbers are binary fractions, and most decimal amounts can't be stored exactly:

```js
0.1 + 0.2          // 0.30000000000000004
4.35 * 100         // 434.99999999999994
```

The errors are tiny, and then they are rounded the wrong way on a receipt. The standard fix is to store **whole cents** — integers are exact — and only turn them into dollars when you *display* them:

```js
const products = [{ id: 'tea', name: 'Moon tea', price: 450 }]   // $4.50

const money = (cents) => `$${(cents / 100).toFixed(2)}`
money(450)    // '$4.50'
money(2100)   // '$21.00'
```

`toFixed(2)` always shows two decimals, so `$21.00`, never `$21`.

The cart's state is just **quantities by product id**: `{ tea: 2, mug: 1 }`. Everything else — how many items, line totals, the subtotal — is derived from that and the product list.

=== webp-11 | Shopping cart, part 3: totals, discounts and shipping
--- teach
Totals are a chain of derived values, and the order of the chain is a business rule, so write it down before you code it:

1. **subtotal** = the sum of the line totals
2. **discount** = 10% of the subtotal with a valid code, else 0 — rounded to a whole cent (`Math.round`)
3. **shipping** = free when *subtotal minus discount* is at least $50.00; otherwise $5.00; and nothing at all for an empty cart
4. **total** = subtotal − discount + shipping

Is free shipping decided before or after the discount? Shops differ; the point is to decide, and to test the edge where it matters — an order just over $50 that drops under it with the code.

```js
function totals() {
  const subtotal = lines().reduce((sum, line) => sum + line.total, 0)
  const discount = state.code ? Math.round(subtotal / 10) : 0
  const afterDiscount = subtotal - discount
  const shipping = subtotal === 0 || afterDiscount >= 5000 ? 0 : 500
  return { subtotal, discount, shipping, total: afterDiscount + shipping }
}
```

=== webp-12 | Shopping cart, part 4: checkout
--- teach
The last step takes the shopper's money — so it takes the most care, even in a practice shop.

**Progressive disclosure.** The checkout form stays hidden until the shopper asks for it, and the Checkout button is disabled while the cart is empty (there is nothing to buy). When the form appears, move focus to its first field: they pressed a button to start typing, so put the cursor there.

**Validate at the boundary.** You know this from earlier: `novalidate` on the form, check the fields yourself, and one clear message saying what to fix. The email check can lean on the browser — `input.validity.typeMismatch` is true for a badly shaped address in a `type="email"` field.

**Finish the transaction completely.** After a successful order:

1. show a confirmation that restates what was bought (the number of items and the amount charged) — computed *before* you empty the cart
2. empty the cart and forget the discount code
3. hide and reset the form (`form.reset()` clears its fields)

```js

const count = itemCount()
confirmation.textContent = `Thanks, ${name}! Your ${count} items (${money(t.total)}) are on their way.`
state.cart = {}
state.code = null
```

The order of those lines matters: read the totals first, then clear. It's the kind of bug that shows "$0.00" on every receipt.

=== webp-14 | Capstone: unit converter
--- teach
Another spec, another empty page. This one is about designing a small piece of logic well.

Converting between four units could mean twelve formulas (km→mi, mi→km, km→ft, …). A better design goes through **one base unit**: convert the amount *into* metres, then *out of* metres into the target unit. Each unit then needs only one number — how many metres it is:

```js
const METRES = { m: 1, km: 1000 }        // add a unit: add one entry
const convert = (value, from, to) => (value * METRES[from]) / METRES[to]
```

Adding a fifth unit is one line, and no pair of units can be forgotten. When you find yourself writing a formula for every combination of things, look for a hub like this.

The display rule in the spec — at most two decimals, with no trailing zeros — has a neat idiom: `Number(x.toFixed(2))` rounds to two places and converting back to a number drops the zeros (`String(Number((6.2137).toFixed(2)))` is `'6.21'`, `String(Number((1000).toFixed(2)))` is `'1000'`).

A `type="number"` input gives you an empty string for anything that isn't a number, so "not a number" and "empty" arrive as the same case. Handle it with a message instead of `NaN km`.

A **swap** button is a small feature that shows whether your state is right: if the units live in state, swapping is exchanging two values and rendering.

- `#result` shows like `10 km = 6.21 mi` — the amount as entered, the converted value rounded to at most two decimals with no trailing zeros

=== webp-15 | Capstone: a sortable, searchable contact list
--- teach
The last capstone combines most of what these courses covered: rendering a list from data, deriving a filtered and sorted view, a form with validation, delegated events and an empty state. The spec fixes what the page must do and the ids it uses; the structure is yours.

Some decisions worth making on purpose before you write code:

- **What is state, and what is derived?** The contacts, the search text, the sort field and the direction are state. The visible list and the count are derived — compute them in one function and draw them in `render()`.
- **How does a contact know which one it is?** Removing "the third one" breaks as soon as the list is sorted or filtered. Give each contact a stable id when the page starts (and when one is added) and put it on its element.
- **Sort with care.** `localeCompare` for text. A tie (two contacts at the same company) needs a rule, or the order will look random: the spec says ties go by name.
- **Where does validation live?** At the form's submit, before anything touches the state.

Then build in small steps, checking the page after each: render the list; add search; add sorting; add the count and empty message; add the form; add removal. Each step is a small change to state, the derived view, or a handler — if a step feels big, the structure needs another look.

<script>
  const contacts = [
    { name: 'Mae Jemison', email: 'mae@nasa.example', company: 'NASA' },
    { name: 'Ada Lovelace', email: 'ada@engines.example', company: 'Analytical Engines' },
    { name: 'Yuri Gagarin', email: 'yuri@vostok.example', company: 'Vostok' },
    { name: 'Sally Ride', email: 'sally@nasa.example', company: 'NASA' },
    { name: 'Chris Hadfield', email: 'chris@csa.example', company: 'CSA' },
    { name: 'Valentina Tereshkova', email: 'valentina@vostok.example', company: 'Vostok' },
    { name: 'Katherine Johnson', email: 'katherine@nasa.example', company: 'NASA' },

  let nextId = 1
  const state = {
    contacts: contacts.map((c) => ({ ...c, id: nextId++ })),

    sortKey: 'name',

    const q = state.query.trim().toLowerCase()
