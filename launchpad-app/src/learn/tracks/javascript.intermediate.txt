=== js2-01 | map, filter and reduce in depth
--- teach
You met `map`, `filter` and `reduce` in the basics. Now look at what they really hand your callback. Every one of them calls it with **three** arguments: the item, its index, and the whole array.

```js
const names = ['ada', 'lin', 'sam']
names.map((name, i) => `${i + 1}. ${name}`)   // ['1. ada', '2. lin', '3. sam']
```

`reduce` is the most general of the three. Its callback gets the **accumulator** (the result so far) and the current item, and whatever it returns becomes the accumulator for the next item. The second argument to `reduce` is where the accumulator starts. It does not have to be a number: an object works just as well, and that is how you turn an array into a lookup table.

```js
const people = [{ id: 7, name: 'ada' }, { id: 9, name: 'lin' }]
const byId = people.reduce((table, person) => {
  table[person.id] = person
  return table
}, {})
byId[9].name   // 'lin'
```

Two mistakes catch almost everyone:

- **Forgetting to return the accumulator.** With braces `{ … }` an arrow function returns nothing unless you write `return`, so the next step receives `undefined` and the code crashes with a confusing message.
- **Leaving out the starting value.** Without it, `reduce` uses the first item as the start, which is wrong for anything but plain sums, and `[].reduce(fn)` throws `TypeError: Reduce of empty array with no initial value`. Always pass one.

Finally, `map` is for building a new array. If you only want to *do* something for each item (print it, save it), use `for…of` or `forEach`; a `map` whose result nobody reads tells the next reader the wrong story.

=== js2-02 | find, some, every and flatMap
--- teach
Four more array methods answer questions you would otherwise write loops for:

```js
const users = [
  { name: 'ada', role: 'admin', verified: true, skills: ['js', 'sql'] },
  { name: 'lin', role: 'member', verified: false, skills: ['python'] },
]
users.find((u) => u.name === 'lin')      // the first match: lin's object
users.find((u) => u.name === 'zoe')      // undefined — nothing matched
users.some((u) => u.role === 'admin')    // true — at least one passes
users.every((u) => u.verified)           // false — not all of them pass
users.flatMap((u) => u.skills)           // ['js', 'sql', 'python']
```

- `find` returns the **item**, or `undefined` when nothing matches. (`findIndex` gives the position, or `-1`.)
- `some` and `every` return booleans, and stop as soon as they know the answer.
- `flatMap` maps each item to an array and joins the arrays into one — the tidy way to collect "all the X of all the Y".

Two things to watch. First, `undefined` leaks: if your function promises "the user, or `null`", convert with `?? null` rather than handing callers an `undefined` they did not expect. Second, `every` on an **empty** array is `true` and `some` is `false`. That is not a bug — "every item in an empty list is verified" has no counter-example — but it surprises people, so decide on purpose what an empty list should mean for your code.

=== js2-03 | Debugging: the sort that sorts wrong
--- teach
This lesson is about a bug, and about how to hunt one down. The method is the same every time:

1. **Reproduce it** with the smallest input that shows the problem.
2. **Read what actually happened**, not what you expected. Print the values.
3. **Check your assumptions** — the bug usually lives in something you "knew" was true.
4. **Fix the cause**, not the symptom, then prove it with the original input and a few edge cases.

Here is an assumption that fails constantly: "`sort()` sorts numbers."

```js
[100, 25, 3].sort()        // [100, 25, 3]  — what?
['b', 'a', 'c'].sort()     // ['a', 'b', 'c']
```

With no argument, `sort` converts every item to a **string** and compares the strings letter by letter. `'100'` comes before `'25'` because `'1'` comes before `'2'`. To sort by anything else, pass a **comparator**: a function `(a, b)` that returns a **negative number** if `a` goes first, a **positive number** if `b` goes first, and `0` if they tie.

```js
[100, 25, 3].sort((a, b) => a - b)   // [3, 25, 100]
[100, 25, 3].sort((a, b) => b - a)   // [100, 25, 3], highest first
['lin', 'ada'].sort((a, b) => a.localeCompare(b))   // ['ada', 'lin']
```

A comparator that returns `true`/`false` (like `(a, b) => a > b`) is a classic bug: `false` counts as `0`, "a tie", so the engine is never told to move `a` after `b`, and the result depends on the engine and the input.

The second trap: **`sort` changes the array you call it on** and returns that same array. If a caller passes you their data and you sort it, you have reordered their array behind their back. Copy first — `[...items].sort(…)` — or use `items.toSorted(…)`, which returns a new array.

To sort by one key and break ties with another, fall through when the first comparison is `0`: `b.score - a.score || a.name.localeCompare(b.name)`.

=== js2-04 | Destructuring, spread and rest
--- teach
**Destructuring** pulls values out of objects and arrays into variables, and it works in function parameters too, which is where it shines:

```js
const user = { name: 'Ada', address: { city: 'London' } }
const { name, role = 'guest' } = user          // role was missing, so the default is used
const { address: { city } } = user             // reach inside: city is 'London'
const [first, second] = ['gold', 'silver', 'bronze']
const [winner, ...others] = ['gold', 'silver', 'bronze']   // others: ['silver', 'bronze']
```

A default only applies when the value is `undefined` — not when it is `null` or `0`. And destructuring something that is missing blows up: `const { address: { city } } = {}` throws, because there is no `address` to look inside. Give the nested object a default too: `{ address: { city } = {} }`.

The same three dots do two opposite jobs:

- **Rest** collects "everything else" into an array or object. In a parameter list, `function sum(...nums)` takes any number of arguments as a real array.
- **Spread** expands an array or object in place: `Math.max(...nums)`, `[...a, ...b]`, `{ ...defaults, ...options }`.

With object spread, **later keys win**. That makes it the idiomatic way to apply settings over defaults:

```js
const defaults = { retries: 3, timeout: 1000 }
const settings = { ...defaults, timeout: 5000 }   // { retries: 3, timeout: 5000 }
```

Put the defaults first. `{ ...options, ...defaults }` would quietly throw away everything the caller asked for.
--- task

- `average(...nums)` — take any number of arguments with rest and return their mean, or `0` when there are none.
- `withDefaults(options)` — return a new object with `retries: 3` and `timeout: 1000`, overridden by anything in `options`.

=== js2-05 | Debugging: the shared shopping cart
--- teach
Objects and arrays are held by **reference**. A variable does not contain the object; it points at it. Assigning it to another variable copies the pointer, so both names now reach the very same object:

```js
const a = { tags: ['x'] }
const b = a
b.tags.push('y')
a.tags        // ['x', 'y'] — there was only ever one object
```

Spread makes a **shallow copy**: a new outer object, but its properties are copied as they are, and a property that is itself an array or object is still the *same* array or object.

```js
const original = { name: 'cart', items: ['apple'] }
const copy = { ...original }
copy.name = 'other'          // fine: copy has its own name
copy.items.push('pear')      // oops: original.items changed too
```

To change something without touching the original, copy **every level you are about to change**:

```js
const original = { name: 'cart', items: ['apple'] }
const next = { ...original, items: [...original.items, 'pear'] }
original.items    // ['apple'] — untouched
next.items        // ['apple', 'pear']
```

This style — return a new value instead of editing the old one — is called an **immutable update**. It is how React state and most data libraries expect you to work, and it removes a whole class of bugs where one part of a program edits data another part is still using. `structuredClone(obj)` makes a full deep copy when you really need one, but copying only the levels you change is cheaper and says more about your intent.

When you debug "data changing by itself", the question to ask is: **which other variable points at this same object?** Log with `console.log(a === b)` to find out.

=== js2-06 | Strings and regular expressions
--- teach
A **regular expression** (regex) is a small pattern language for text. You write it between slashes:

```js
/\d+/.test('order 66')            // true — "one or more digits" appears
'a1b22c333'.match(/\d+/g)          // ['1', '22', '333'] — g means "all matches"
'Hello'.replace(/l/g, 'L')         // 'HeLLo'
```

The pieces you will use most: `\d` a digit, `\w` a letter, digit or underscore, `\s` whitespace, `.` any character, `[a-z]` a range, `[^a-z]` anything *not* in it, `+` one or more, `*` zero or more, `?` optional, `{4}` exactly four, `^` and `$` the start and end. Flags go after the closing slash: `g` (every match), `i` (ignore case).

**Groups** in brackets capture parts of a match, and you can name them with `(?<name>…)`:

```js
const m = /^(?<user>\w+)@(?<host>[\w.]+)$/.exec('ada@example.com')
m.groups.user    // 'ada'
m.groups.host    // 'example.com'
```

`exec` returns `null` when there is no match — check for that before reading `.groups`. To loop over every match with its groups, use `text.matchAll(/…/g)`.

Common mistakes: forgetting `^` and `$`, so `/\d{4}/` happily "matches" `'12345678'`; forgetting that `.` means any character (write `\.` for a real dot); and forgetting the `g` flag on `replace`, which then changes only the first match. Regex is powerful but hard to read — name your groups, keep each pattern to one job, and test it on inputs that should *not* match as well as ones that should.

const LOG_LINE = /^(?<date>\d{4}-\d{2}-\d{2}) (?<time>\d{2}:\d{2}:\d{2}) (?<level>DEBUG|INFO|WARN|ERROR) \[(?<module>[\w-]+)\] (?<message>.*)$/

function parseLogLine(line) {
  const m = LOG_LINE.exec(line)
  if (!m) return null
  const { date, time, level, module, message } = m.groups
  return { date, time, level, module, message }
}

function slugify(title) {
  return title
    .toLowerCase()
    .replace(/[^a-z0-9]+/g, '-')
    .replace(/^-+|-+$/g, '')
}

function hashtags(text) {
  const seen = []
  for (const m of text.matchAll(/#(\w+)/g)) {
    const tag = m[1].toLowerCase()
    if (!seen.includes(tag)) seen.push(tag)
  }
  return seen
}

=== js2-07 | Closures: functions that remember
--- teach
A function can use variables from the place where it was **written**, not just its own. When an inner function is returned and outlives the outer one, it keeps those variables alive. That pairing — a function plus the variables it can still reach — is a **closure**.

```js
function makeGreeter(greeting) {
  return (name) => `${greeting}, ${name}!`
}
const hello = makeGreeter('Hello')
const howdy = makeGreeter('Howdy')
hello('Ada')   // 'Hello, Ada!'
howdy('Lin')   // 'Howdy, Lin!'
```

Each call to `makeGreeter` creates a fresh `greeting` variable, so `hello` and `howdy` remember different ones. The same trick gives you **private state**: a variable only your returned functions can see.

```js
function makeWallet() {
  let balance = 0                       // nobody outside can touch this
  return {
    deposit(n) { balance += n },
    balance: () => balance,
  }
}
const w = makeWallet()
w.deposit(5)
w.balance()      // 5
w.balance = 99   // replaces the method, but the real balance is still 5 inside
```

`deposit(n) { … }` inside an object literal is **method shorthand**: a property whose value is a function. `balance: () => balance` is the same idea written with an arrow.

The classic closure trap is a loop with `var`:

```js
for (var i = 0; i < 3; i++) setTimeout(() => console.log(i), 0)   // 3 3 3
for (let j = 0; j < 3; j++) setTimeout(() => console.log(j), 0)   // 0 1 2
```

`var` makes **one** `i` shared by the whole loop, and by the time the timers fire it is 3. `let` makes a new `j` for each pass, so each closure remembers its own. This is one more reason to never use `var`.

=== js2-08 | Higher-order functions
--- teach
A **higher-order function** takes a function, returns a function, or both. You have used them all along — `map` takes one — but writing your own is how you package up a *behaviour* and reuse it.

A function that returns a function can configure it first:

```js
const multiplyBy = (factor) => (n) => n * factor
const double = multiplyBy(2)
[1, 2, 3].map(double)     // [2, 4, 6]
```

A function that takes a function can wrap it with extra behaviour — logging, timing, caching, retrying — without the wrapped function knowing:

```js
function logged(fn) {
  return (...args) => {
    const result = fn(...args)
    console.log(fn.name, args, '->', result)
    return result
  }
}
const add = (a, b) => a + b
const loudAdd = logged(add)
loudAdd(2, 3)   // prints: add [ 2, 3 ] -> 5, and returns 5
```

Notice `(...args) => fn(...args)`: rest collects whatever arguments come in and spread passes them all on, so the wrapper works for any function.

Comparators are a great place for this. Instead of writing `(a, b) => …` by hand every time you sort, write a function that **builds** comparators. One warning: `a - b` only works for numbers. For strings it gives `NaN`, and a comparator returning `NaN` leaves the order unpredictable. Compare with `<` and `>` and return `-1`, `1` or `0`, which works for numbers and strings alike.
--- task

- `once(fn)` — returns a function that calls `fn` (with whatever arguments it gets) the first time, and on every later call returns that first result without calling `fn` again.
- `by(keyFn)` — returns a comparator that orders items by `keyFn(item)`, smallest first. It must work when the keys are numbers **or** strings.
- `reversed(compare)` — returns a comparator that orders things the opposite way to `compare`.

--- solution
function once(fn) {
  let called = false
  let result
  return (...args) => {
    if (!called) {
      called = true
      result = fn(...args)
    }
    return result
  }
}

function by(keyFn) {
  return (a, b) => {
    const ka = keyFn(a)
    const kb = keyFn(b)
    if (ka < kb) return -1
    if (ka > kb) return 1
    return 0
  }
}

function reversed(compare) {
  return (a, b) => compare(b, a)
}

=== js2-09 | Errors: throw, catch, finally and your own error types
--- teach
An error is an object. `throw` hands it up the call stack until a `try`/`catch` catches it or the program stops. `finally` runs on the way out either way — the place for clean-up.

```js
function readConfig(text) {
  try {
    return JSON.parse(text)
  } catch (err) {
    console.log('bad config:', err.message)
    return {}
  } finally {
    console.log('done reading')
  }
}
readConfig('{oops')   // prints both lines and returns {}
```

Built-in types include `Error`, `TypeError`, `RangeError` and `SyntaxError`. For your own failures, make a **subclass** so callers can tell your errors apart from bugs. A `class` describes a kind of object (lesson 12 covers classes fully); `class NotFoundError extends Error` makes a new kind of error with everything an `Error` has. Its `constructor` runs when you write `new NotFoundError(…)`, `super(…)` runs `Error`'s own constructor first, and `this` is the new error object:

```js
class NotFoundError extends Error {
  constructor(what) {
    super(`${what} not found`)     // sets message
    this.name = 'NotFoundError'    // shows up in logs as "NotFoundError: …"
    this.what = what               // any extra data callers need
  }
}
const e = new NotFoundError('user 7')
e instanceof NotFoundError   // true
e instanceof Error           // true
e.message                    // 'user 7 not found'
```

The big mistake is the **catch-all that swallows everything**:

```js
function saveUser(user) {
  try { save(user) } catch { return 'invalid input' }
}
```

If `save` has a typo in it, that `TypeError` is now reported as "invalid input" and you will spend an afternoon looking in the wrong place. Catch only what you expect — check with `instanceof` — and **re-throw** everything else with `throw err`.

=== js2-10 | JSON: parse, stringify and validate
--- teach
JSON is text. `JSON.stringify` turns a value into it, `JSON.parse` turns it back:

```js
JSON.stringify({ name: 'launch', tags: ['a'] })   // '{"name":"launch","tags":["a"]}'
JSON.stringify({ a: 1 }, null, 2)                 // pretty-printed, 2 spaces
JSON.parse('{"n": 1}').n                           // 1
```

JSON only knows strings, numbers, booleans, `null`, arrays and plain objects. Everything else is changed on the way through, and this is where bugs come from:

- A `Date` becomes an ISO **string** (Dates have a `toJSON` method), and `JSON.parse` does not turn it back.
- `undefined` and functions vanish from objects; `NaN` and `Infinity` become `null`.
- `Map` and `Set` become `{}`.

`JSON.parse` takes an optional **reviver**, a function called for every key and value on the way in. Whatever it returns is used instead:

```js
const text = '{"at":"2026-01-02T03:04:05.000Z"}'
const data = JSON.parse(text, (key, value) => (key === 'at' ? new Date(value) : value))
data.at instanceof Date    // true
```

Three checks help with shapes: `Array.isArray(x)` (is it an array?), `'name' in obj` (does the object have that key?) and `typeof`. `new Date(text)` makes a date; text it cannot read gives an Invalid Date.

And `JSON.parse` **throws** a `SyntaxError` on bad input. Anything that reads JSON from outside your program — a file, a request, local storage — must expect that, and must also check the *shape*: valid JSON can still be `[1, 2]` or `null` when you expected an object, or be missing a field. Parse, then validate, then use — and report *what* was wrong, so the person fixing the input knows where to look.

=== js2-11 | Map and Set
--- teach
A plain object is a fine record, but a poor general-purpose dictionary: its keys are always strings (so `1` and `'1'` collide), it has inherited keys like `toString`, and it has no size. **`Map`** is built for the job:

```js
const visits = new Map()
visits.set('ada', 1)
visits.set('ada', visits.get('ada') + 1)
visits.get('ada')       // 2
visits.has('zoe')       // false
visits.size             // 1
[...visits]             // [['ada', 2]] — entries, in insertion order
```

A `Map` keeps keys in the order they were first added, accepts any value as a key (numbers, objects), and is fast to add to and look up in, even with millions of entries.

A **`Set`** holds each value at most once:

```js
const tags = new Set(['js', 'css', 'js'])
tags.size               // 2
tags.has('css')         // true
[...new Set([3, 1, 3, 2, 1])]   // [3, 1, 2] — de-duplicate, keeping first-seen order
```

The reason to reach for them is not only tidiness, it is **speed**. `array.includes(x)` looks at every item, so calling it inside a loop over another array is slow for large inputs: 100,000 × 100,000 comparisons. `set.has(x)` takes about the same time however big the set is. When you catch yourself searching an array inside a loop, build a `Set` or `Map` first.

=== js2-12 | Classes: getters, setters and static members
--- teach
A **class** is a template for objects that share behaviour:

```js
class Rect {
  constructor(width, height) {
    this.width = width
    this.height = height
  }
  area() {
    return this.width * this.height
  }
}
new Rect(2, 3).area()   // 6
```

Three features make classes more than bags of methods.

**Getters and setters** look like properties but run code. A getter computes a value on demand; a setter can validate before storing:

```js
class Circle {
  constructor(r) { this.radius = r }
  get diameter() { return this.radius * 2 }
  set diameter(d) { this.radius = d / 2 }
}
const c = new Circle(1)
c.diameter        // 2 — no brackets, it reads like a property
c.diameter = 10
c.radius          // 5
```

**Private fields** start with `#` and cannot be read or written from outside the class at all — not even by `Object.keys` or `JSON.stringify`. Pair them with a getter and setter and every write goes through your validation.

**Static members** belong to the class itself, not to each object: constants (`static MAX = 10`) and alternative constructors (`static fromJSON(text)`), called as `Circle.fromJSON(…)`.

A classic mistake: a setter that assigns to its own name. `set radius(r) { this.radius = r }` calls itself forever and crashes with "Maximum call stack size exceeded". Store the value in a differently named (usually private) field. And set things through the setter in the constructor too, so the rules apply from the very first value.

=== js2-13 | Debugging: == versus === and truthiness
--- teach
JavaScript is happy to convert values for you, and most of its surprising bugs come from that.

**Truthiness.** In an `if`, or with `||` and `&&`, every value counts as true or false. The **falsy** values are `false`, `0`, `''`, `null`, `undefined` and `NaN`. Everything else is truthy — including `'0'`, `'false'`, `[]` and `{}`.

So `x || fallback` means "use the fallback if `x` is **falsy**", which is not the same as "if `x` is missing":

```js
const qty = 0
qty || 1        // 1 — the real 0 was thrown away
qty ?? 1        // 0 — ?? only replaces null and undefined
```

**Loose equality.** `==` converts both sides before comparing, by rules few people remember:

```js
0 == ''         // true
0 == '0'        // true
'' == '0'       // false — so == is not even consistent
null == 0       // false
null == undefined   // true
```

`===` compares without converting: different types are never equal. Use it always, and when two values really are of different types (an id from a URL is a string; the id in your data is a number), **convert explicitly** — `Number(text)` — and check the conversion worked, so you decide what a blank or garbage value means instead of letting `==` decide for you.

When debugging, print the **type** as well as the value: `console.log(typeof id, JSON.stringify(id))`. `'0'` and `0` look identical in a plain `console.log`.
--- task

=== js2-14 | Problem solving: counting and grouping at scale
--- teach
A huge number of real problems are "count things" or "group things" in disguise: the most common error in a log, the busiest customer, orders by month. Here is how to approach a problem like this — or any problem.

1. **Restate it** in your own words, and write down small examples with their answers, including the awkward ones: empty input, ties, one item.
2. **Solve it slowly first.** The obvious way to count words: for each distinct word, walk the whole list and count matches. It is correct, and it is a good thing to compare against.
3. **Find the waste.** The slow version walks the list once *per distinct word*. With 300,000 words and 30,000 distinct ones that is 9 billion steps — minutes, not milliseconds.
4. **Improve.** Walk the list **once**, keeping a running tally in a `Map`:

```js
const counts = new Map()
for (const w of ['a', 'b', 'a']) counts.set(w, (counts.get(w) ?? 0) + 1)
[...counts]    // [['a', 2], ['b', 1]]
```

One pass, one lookup per word: fast however long the input. Grouping is the same pattern, with an array per key instead of a number.

Two small tools for grouping: `x ??= value` assigns only when `x` is `null` or `undefined`, so `groups[key] ??= []` creates the array the first time a key appears. And because these lessons leave out semicolons, a line that **starts** with `(` or `[` must begin with `;`, or JavaScript reads it as part of the line above: `;(groups[key] ??= []).push(item)`.

5. **Then shape the answer.** To get the top k, turn the Map into entries and sort them — that sort is over the *distinct* words only, which is far fewer. Be exact about ties: "most frequent first, and equal counts in alphabetical order" is a comparator with a tie-break.

Test with the small cases you wrote down, then with something large. A correct but slow answer is still a failing answer when the input is real.
--- task

Return the `k` most frequent as `[word, count]` pairs, highest count first, ties in alphabetical order. If there are fewer than `k` distinct words, return them all; empty text gives `[]`.

function groupBy(items, keyFn) {
  const groups = {}
  for (const item of items) {
    const key = keyFn(item)
    ;(groups[key] ??= []).push(item)

=== js2-15 | Design: untangling code into small pure functions
--- teach
Working code is not finished code. Look at a function that validates, aggregates, sorts and formats all in one loop, while also updating variables outside itself. It works — once. Call it a second time and the totals double, because the outside variables still hold the last run's numbers. It is also impossible to test one step without running all of them.

A **pure function** is one whose result depends only on its arguments, and which changes nothing outside itself: no global variables, no mutation of its inputs, no printing. Pure functions are the easiest code there is to test, reuse, and reason about — the same input always gives the same output.

The refactoring recipe:

1. **Name the steps.** Read the tangled code and write down what it does in plain English: "drop invalid orders; total per customer; sort; format". Each phrase becomes a function.
2. **Move the state inside.** Anything the steps need is an argument; anything they produce is a return value. Variables at the top of the file that the function updates are the first thing to go.
3. **Stop mutating inputs.** Build new arrays and objects instead of editing the ones you were given.
4. **Compose.** The original entry point becomes a short pipeline of the new functions:

```js
const report = (orders) => format(totals(valid(orders)))
```

5. **Keep behaviour identical** — except for the bugs you meant to fix. Checks on the output before and after are your safety net.

A good sign you are done: each function fits on your screen, has a name that says exactly what it returns, and could be tested with a one-line call.
--- task
`report(orders)` works on the first call but returns doubled totals on the second, because it keeps its state in top-level variables. Refactor it into pure functions:

- `validOrders(orders)` — the orders that are not `'cancelled'` and have an `amount` above 0.
- `totalsByCustomer(orders)` — an array of `{ customer, total }`, one per customer, sorted by `total` highest first; customers with equal totals stay in the order they first appeared.
- `formatReport(totals)` — the text: one line per customer, `customer: total` with 2 decimals, then a last line `TOTAL: ` and the grand total with 2 decimals, lines joined by `\n`.
- `report(orders)` — returns `formatReport(totalsByCustomer(validOrders(orders)))`.

No top-level `let` variables, and nothing may change the `orders` array or its objects.
--- starter
let grandTotal = 0
let lines = []

function report(orders) {
  for (let i = 0; i < orders.length; i++) {
    const o = orders[i]
    if (o.status !== 'cancelled' && o.amount > 0) {
      let found = false
      for (let j = 0; j < lines.length; j++) {
        if (lines[j].customer === o.customer) {
          lines[j].total += o.amount
          found = true
        }
      }
      if (!found) lines.push({ customer: o.customer, total: o.amount })
      grandTotal += o.amount
    }
  }
  lines.sort((a, b) => b.total - a.total)
  let out = ''
  for (const l of lines) out += l.customer + ': ' + l.total.toFixed(2) + '\n'
  out += 'TOTAL: ' + grandTotal.toFixed(2)
  return out
}
--- solution
function validOrders(orders) {
  return orders.filter((o) => o.status !== 'cancelled' && o.amount > 0)
}

function totalsByCustomer(orders) {
  const totals = new Map()
  for (const o of orders) totals.set(o.customer, (totals.get(o.customer) ?? 0) + o.amount)
  return [...totals]
    .map(([customer, total]) => ({ customer, total }))
    .sort((a, b) => b.total - a.total)
}

function formatReport(totals) {
  const grand = totals.reduce((sum, t) => sum + t.total, 0)
  return [...totals.map((t) => `${t.customer}: ${t.total.toFixed(2)}`), `TOTAL: ${grand.toFixed(2)}`].join('\n')
}

function report(orders) {
  return formatReport(totalsByCustomer(validOrders(orders)))
}
