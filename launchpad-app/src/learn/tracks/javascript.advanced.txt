=== js3-01 | this: who is calling?
--- teach
The intermediate course covered the idioms working developers use every day. This course goes underneath them — how `this`, prototypes, promises and the event loop really work — and adds the patterns and algorithms that let you design and debug serious programs.

`this` is not decided where a function is written. It is decided **each time the function is called**, by how it is called. Four rules cover almost everything:

1. **Method call** — `obj.method()`: `this` is `obj`, the thing before the dot.
2. **Plain call** — `fn()`: `this` is `undefined` (in strict mode, which modules and classes always use). Reading `this.x` then throws a `TypeError`.
3. **`new`** — `new Fn()`: `this` is the brand-new object being built.
4. **Explicit** — you choose it:
   - `fn.call(obj, a, b)` calls `fn` with `this = obj` and the arguments listed.
   - `fn.apply(obj, [a, b])` is the same with the arguments in an array.
   - `fn.bind(obj)` does not call anything: it returns a **new function** whose `this` is locked to `obj` forever — even `call` cannot change it afterwards.

```js
const ship = {
  name: 'Apollo',
  describe() { return `I am ${this.name}` },
}
ship.describe()                          // 'I am Apollo'
const other = { name: 'Gemini' }
ship.describe.call(other)                // 'I am Gemini'
const locked = ship.describe.bind(ship)
locked()                                 // 'I am Apollo', even as a plain call
```

**Arrow functions are the exception**: they have no `this` of their own and use the `this` of the code around them. That makes them perfect for callbacks *inside* a method, and wrong as methods themselves:

```js
const bad = {
  name: 'x',
  describe: () => `I am ${this?.name}`,   // this is NOT bad; it is the outer this
}
bad.describe()    // 'I am undefined'
```

(`this?.name` is **optional chaining**: it reads `name` only if `this` is not `null` or `undefined`, and gives `undefined` otherwise.)

A method that returns `this` can be **chained**: `list.add(1).add(2)`. Many APIs — array methods, query builders — work that way.

=== js3-02 | Debugging: the lost this
--- teach
`TypeError: Cannot read properties of undefined (reading 'counts')` inside a method is almost always the same bug: the method was **detached** from its object. Here is the method for tracking it down:

1. **Read the error.** It names the property it tried to read (`counts`) and the line. Something before the dot — `this` — was `undefined`.
2. **Find the call site, not the definition.** The method is fine; the question is *how it was called*. Search for places the method is passed as a value without calling it: `arr.forEach(this.record)`, `setTimeout(this.tick, 100)`, `const { format } = formatter`, `button.onclick = obj.handle`.
3. **Confirm it.** `console.log(this)` at the top of the method prints `undefined`.
4. **Fix the cause.**

Why it happens: `this.record` is just a function value. Handing it to `forEach` gives `forEach` the function but *not* the object — and `forEach` calls it as a plain function, so rule 2 applies and `this` is `undefined`. The same goes for a `function () {}` callback written inside a method: it gets its own `this`, which is `undefined`, not the method's.

Three fixes, from local to structural:

```js
class Tally {
  constructor() {
    this.counts = {}
    this.record = this.record.bind(this)        // 3. bind once, in the constructor
  }
  record(word) { this.counts[word] = (this.counts[word] ?? 0) + 1 }
  recordAll(words) {
    words.forEach((w) => this.record(w))       // 1. an arrow keeps the method's this
    words.forEach(this.record, this)           // 2. forEach takes a thisArg
  }
}
```

You can also declare the method as a class field arrow — `record = (word) => { … }` — which gives each object its own bound copy. Binding in the constructor (or the class field) is the right fix when the method is **meant** to be passed around as a callback, because then every caller is safe, not just the one you found.

=== js3-03 | Prototypes: what classes are made of
--- teach
Every object has a hidden link to another object, its **prototype**. When you read a property the object does not have, JavaScript follows the link and looks there, then at *that* object's prototype, and so on up the **prototype chain** until it finds the property or reaches `null`.

```js
const base = { greet() { return `hi from ${this.name}` } }
const ada = Object.create(base)        // a new object whose prototype is base
ada.name = 'Ada'
ada.greet()                            // 'hi from Ada' — found on base, this is ada
Object.getPrototypeOf(ada) === base    // true
Object.keys(ada)                       // ['name'] — greet is not ada's own
```

Before `class` existed, this is how everyone built types — and it is still exactly what `class` does underneath. A function called with `new` creates an object whose prototype is the function's `.prototype` property, runs the function with `this` set to it, and returns it:

```js
function Point(x, y) {
  this.x = x
  this.y = y
}
Point.prototype.norm = function () {
  return Math.hypot(this.x, this.y)
}
const p = new Point(3, 4)
p.norm()                                          // 5
Object.getPrototypeOf(p) === Point.prototype      // true
```

Methods live **once** on the prototype and are shared by every object; only the data is per object. `class Point { norm() {} }` produces the same shape.

Inheritance is a chain two links long: `Dog.prototype`'s own prototype is `Animal.prototype`. You wire it with `Object.create`, call the parent constructor with `Animal.call(this, name)` (what `super(name)` does), and restore `Dog.prototype.constructor = Dog`, which `Object.create` replaced.

Mistakes to avoid: putting methods in the constructor (`this.speak = function …`) copies them onto every object; using arrow functions for prototype methods breaks `this`; and forgetting `Animal.call(this, …)` leaves the parent's fields unset.

=== js3-04 | Promises: creating, chaining and failing
--- teach
A **promise** is an object standing in for a value that is not ready yet. It is *pending*, then settles exactly once: **fulfilled** with a value, or **rejected** with an error.

You rarely need to build one by hand, except to wrap something callback-based such as a timer:

```js
const wait = (ms) => new Promise((resolve) => setTimeout(resolve, ms))
```

`new Promise` runs your function immediately, handing it `resolve` and `reject`. Call one of them when the work is done. If the function throws, the promise rejects.

`.then(fn)` returns a **new** promise, and what `fn` returns decides it:

- return a value → the new promise fulfils with it;
- return a promise → the new promise follows that one;
- throw → the new promise rejects.

That is why chains stay flat, and why errors flow down them to the nearest `.catch`:

```js
Promise.resolve('{"n": 2}')
  .then((text) => JSON.parse(text))
  .then((data) => data.n * 10)
  .catch(() => 0)
  .then((n) => console.log(n))     // 20; with bad JSON it would print 0
```

`.catch` handles a rejection and, like `then`, returns a new promise — so after a `catch` that returns a value, the chain continues *fulfilled*.

The classic bug is **forgetting to return** inside `then`: `.then((x) => { save(x) })` returns `undefined`, so the next step runs before `save` finishes and never sees its errors. The second is wrapping a promise in `new Promise` needlessly. If you already have a promise, chain on it.

=== js3-05 | async/await and running promises together
--- teach
`async`/`await` is promise chaining written as ordinary code. An `async` function always returns a promise; inside it, `await p` pauses until `p` settles, then gives its value — or **throws** its error, so plain `try`/`catch` works.

The skill is choosing how several promises combine:

| Tool | Waits for | Result | Rejects when |
| --- | --- | --- | --- |
| `Promise.all(ps)` | all | array of values, in order | **any** rejects (fails fast) |
| `Promise.allSettled(ps)` | all | `{ status, value }` or `{ status, reason }` for each | never |
| `Promise.race(ps)` | the first to settle | that value | the first to settle rejected |
| `Promise.any(ps)` | the first to **fulfil** | that value | all reject (`AggregateError`) |

```js
const sleep = (ms, v) => new Promise((r) => setTimeout(() => r(v), ms))
await Promise.all([sleep(30, 'a'), sleep(10, 'b')])        // ['a', 'b'] after 30ms, not 40
await Promise.race([sleep(30, 'slow'), sleep(10, 'fast')])  // 'fast'
```

Use `all` when you need every result and one failure spoils the batch; `allSettled` when you want whatever succeeded and a list of what failed; `race` to put a deadline on something (race it against a timer that rejects); `any` to take the first mirror or replica that answers.

Two common mistakes. **Awaiting in a loop** runs the calls one after another: five 40ms requests take 200ms instead of 40. Start them all first, then await them together. And **losing the timer**: a timeout built with `race` leaves its `setTimeout` running after the real work wins; clear it in a `finally` so nothing fires late.
--- task

- `fastest(promises)` — the value of the first promise to **fulfil**, ignoring rejections; if all of them reject, it rejects with an `AggregateError`.

  await sleep(40)
  if (id === 13) throw new Error(`user ${id} not found`)
  return { id, name: `user${id}` }
}

function fetchAll(ids) {
  return Promise.all(ids.map((id) => fetchUser(id)))
}

async function fetchSome(ids) {
  const settled = await Promise.allSettled(ids.map((id) => fetchUser(id)))
  const users = []
  const failed = []
  settled.forEach((s, i) => {
    if (s.status === 'fulfilled') users.push(s.value)
    else failed.push(ids[i])
  })
  return { users, failed }
}

function withTimeout(promise, ms) {
  let timer
  const deadline = new Promise((_, reject) => {
    timer = setTimeout(() => reject(new Error('timed out')), ms)
  })
  return Promise.race([promise, deadline]).finally(() => clearTimeout(timer))
}

function fastest(promises) {
  return Promise.any(promises)
}

=== js3-06 | The event loop: predict, then fix the order
--- teach
JavaScript runs one thing at a time on a single thread. What decides *what runs next* is the **event loop**, and knowing its rules lets you predict the order of any async code.

1. **Synchronous code runs to the end first.** Nothing interrupts it — not a timer set to 0ms, not a resolved promise.
2. Then the **microtask queue** is emptied, completely: promise callbacks (`.then`, `.catch`, `.finally`), `queueMicrotask`, and the rest of an `async` function after an `await`. Microtasks queued by microtasks run in the same round.
3. Only then does one **task** (macrotask) run — a `setTimeout` callback, for example — followed again by all microtasks, and so on.

```js
const order = []
setTimeout(() => order.push('timer'), 0)
Promise.resolve().then(() => order.push('promise'))
order.push('sync')
await new Promise((r) => setTimeout(r, 5))
console.log(order)   // [ 'sync', 'promise', 'timer' ]
```

The starter's `trace()` uses `;(async () => { … })()`: an async arrow function defined and called at once, with the leading `;` because the line starts with `(`. An `async` function runs **synchronously up to its first `await`**, then returns to its caller; the rest of its body becomes a microtask queued when the awaited value is ready. `await null` still pauses — it just resumes on the next microtask round.

This is why a timeout of 0 is not "now", and why code like this is broken:

```js
function save(log) {
```

=== js3-07 | Debugging: the promise nobody waited for
--- teach
Async bugs rarely crash. Instead a number comes out as `0`, a list is half-empty, or a total is short — and the results change from run to run. Two causes account for most of them.

**The floating promise.** An async function returns a promise immediately. If nobody `await`s it, the code after it runs before the work is done, and any error it throws is lost. The sneakiest version is `forEach` with an async callback:

```js
const sleep = (ms) => new Promise((r) => setTimeout(r, ms))
const saved = []
const rows = ['a', 'b', 'c']
rows.forEach(async (row) => {
  await sleep(10)          // forEach does not wait for this…
  saved.push(row)
})
console.log('done, saved', saved.length)   // …so this prints: done, saved 0
```

`forEach` calls your callback, gets a promise back, and throws it away. It never waits. Use `for…of` with `await` (one at a time, in order), or `await Promise.all(rows.map(…))` (all at once, when order and overlap do not matter).

**The lost update.** Two async tasks each read a value, wait, then write back a new one:

```js
const sleep = (ms) => new Promise((r) => setTimeout(r, ms))
let balance = 0
async function deposit(amount) {
  const current = balance        // both calls read 0…
  await sleep(10)
  balance = current + amount     // …and each writes back 0 + its own amount
}
await Promise.all([deposit(10), deposit(20)])
console.log(balance)   // 20, not 30
```

Each overwrites the other, and the total comes out wrong. Any `await` between reading shared state and writing it opens this gap. Fix it by not overlapping those steps: do the updates in sequence, or compute the whole change first and write once.

The debugging method: **make it visible**. Log with timestamps (`console.log(Date.now(), 'insert start', row)`) and you will see the order you assumed is not the order that happened. Then look at every call to an async function and ask: *who awaits this promise?* If the answer is nobody, that is your bug. (Linters have a rule for exactly this: `no-floating-promises`.)

=== js3-08 | Iterators and generators
--- teach
`for…of`, spread (`[...x]`) and destructuring all work on anything **iterable**. An object is iterable if it has a method under the key `Symbol.iterator` that returns an **iterator**: an object with a `next()` method returning `{ value, done }`.

```js
const it = [10, 20][Symbol.iterator]()
it.next()    // { value: 10, done: false }
it.next()    // { value: 20, done: false }
it.next()    // { value: undefined, done: true }
```

Writing iterators by hand is fiddly. A **generator function** (`function*`) writes them for you: calling it returns an iterator, and each `yield` hands out one value, pausing the function until the next `next()`.

```js
function* countdown(n) {
  while (n > 0) yield n--
}
[...countdown(3)]    // [3, 2, 1]
```

(Swapping two variables in one step is array destructuring: `;[a, b] = [b, a + b]` — with a leading `;`, because the line starts with `[`.)

Because a generator pauses, it can describe an **infinite** sequence and only compute as much as you ask for. That makes generators the natural way to write lazy helpers such as `take`, `map` or `filter` over any iterable.

To make your own class iterable, give it a generator method named `[Symbol.iterator]`:

```js
class Pair {
  constructor(a, b) { this.a = a; this.b = b }
  *[Symbol.iterator]() { yield this.a; yield this.b }
}
[...new Pair('x', 'y')]   // ['x', 'y']
```

Watch out for two things. A generator object can be consumed **only once** — spread it twice and the second time is empty — so a reusable collection should create a fresh generator each time `[Symbol.iterator]()` is called (a generator method does). And never spread an infinite generator: `[...naturals()]` never finishes. Cut it down with something like `take` first.

=== js3-09 | Debounce and throttle
--- teach
Some events fire far more often than you want to react to them: key presses in a search box, scroll and resize events, a sensor streaming readings. Two classic higher-order functions tame them, and both are built from a closure plus a timer.

**Debounce** waits for a pause. Each call cancels the previous timer and starts a new one; the function only runs once the calls have stopped for `ms` milliseconds, with the **latest** arguments. Use it for "search after the user stops typing".

```js
function debounce(fn, ms) {
  let timer
  return (...args) => {
    clearTimeout(timer)
    timer = setTimeout(() => fn(...args), ms)
  }
}
```

**Throttle** guarantees a maximum rate. The first call runs straight away, and further calls are ignored until `ms` milliseconds have passed since the last run. Use it for "update the position at most every 100ms while scrolling". Throttle does not need a timer at all: remember *when* it last ran, and compare with `Date.now()`.

The difference in one picture, for calls at 0, 10, 20 and 100ms with `ms = 50`:

- debounced: runs once at 70ms (with the 20ms arguments), then at 150ms (with the 100ms ones).
- throttled: runs at 0ms and at 100ms; the calls at 10 and 20 are dropped.

The mistakes: creating the timer variable **inside** the returned function (then every call has its own timer and nothing is cancelled); passing the *first* arguments instead of the latest; and calling `debounce(fn, 300)` afresh on every event instead of once — each call makes a brand-new debounced function with its own empty memory.

=== js3-10 | Memoisation
--- teach
**Memoisation** means remembering a function's answers. The first call with some arguments does the work and stores the result under a key made from the arguments; later calls with the same arguments return the stored result instantly.

```js
function memoize(fn) {
  const cache = new Map()
  return (n) => {
    if (!cache.has(n)) cache.set(n, fn(n))
    return cache.get(n)
  }
}
```

For several arguments you need a key that represents all of them — `JSON.stringify(args)` is a simple one for numbers and strings (`[1, 2]` and `[2, 1]` give different keys, as they should).

It pays off enormously for **recursive** functions that solve the same sub-problem again and again. Counting the ways to climb `n` stairs taking 1, 2 or 3 at a time:

```js
function ways(n) {
  if (n < 0) return 0
  if (n === 0) return 1
  return ways(n - 1) + ways(n - 2) + ways(n - 3)
}
```

`ways(40)` calls `ways(37)` from three different places, each of which calls `ways(34)`… the number of calls grows roughly 1.8 times with every step up. `ways(40)` makes billions of calls. With memoisation, each `ways(k)` is computed once: 40 calls.

The catch that trips everyone up: memoising a recursive function only helps if the **recursive calls go through the memoised version**. `const fast = memoize(ways)` caches the outer call, but `ways` still calls the slow `ways` inside. Define the function *as* the memoised one: `const ways = memoize((n) => … ways(n - 1) …)`.

Two more rules. Only memoise **pure** functions — caching `fetchPrice()` would serve yesterday's price for ever. And check with `cache.has(key)`, not `if (cache.get(key))`: a remembered `0`, `''` or `undefined` is still an answer.

=== js3-11 | Problem solving: an LRU cache
--- teach
A cache keeps recent answers close at hand, but memory is finite, so it needs an **eviction policy**: what to throw out when it is full. The most popular is **LRU — least recently used**: when there is no room, drop the item that has gone longest without being read or written.

Work the problem before coding it. Capacity 2:

```
put(a, 1)   cache, oldest first: a
put(b, 2)                        a b
get(a)      → 1                  b a      (reading a makes it the most recent)
put(c, 3)   full: evict b        a c
get(b)      → undefined          a c
put(a, 9)   update, no eviction  c a
```

Now the operations you need: find by key, move an item to the "most recent" end, and remove from the "oldest" end — all of them **on every call**.

A first attempt with an array of keys works: `indexOf` to find, `splice` to move, `shift` to evict. But each of those walks the array, so with 50,000 items and 300,000 calls you are doing billions of steps.

The key insight for JavaScript: **a `Map` remembers insertion order**, and deleting and re-inserting a key moves it to the end. So the Map *is* the recency list:

- the most recent key is the last one; the least recent is the first — `map.keys().next().value`;
- "touch" a key: `map.delete(key)` then `map.set(key, value)`;
- all of these take the same small time however big the Map is.

Edge cases to decide up front: updating an existing key must not evict anything; values can be falsy (`0`, `''`), so test with `has`, not with the value; and capacity 1 must still work.
--- task
Write `class LRUCache`:

- `new LRUCache(capacity)`
- `get(key)` — the value, or `undefined` if the key is not cached. A successful get makes the key the most recently used.
- `put(key, value)` — stores the value (updating it if the key exists) and makes the key the most recently used. If that takes the cache above `capacity`, evict the least recently used key.
- a `size` getter — how many keys are cached.
- `keys()` — an array of the cached keys, least recently used first.

It will be given 300,000 operations with a capacity of 50,000.

--- solution
class LRUCache {
  constructor(capacity) {
    this.capacity = capacity
    this.map = new Map()
  }

  get(key) {
    if (!this.map.has(key)) return undefined
    const value = this.map.get(key)
    this.map.delete(key)
    this.map.set(key, value)
    return value
  }

  put(key, value) {
    if (this.map.has(key)) this.map.delete(key)
    this.map.set(key, value)
    if (this.map.size > this.capacity) this.map.delete(this.map.keys().next().value)
  }

  get size() {
    return this.map.size
  }

  keys() {
    return [...this.map.keys()]
  }
}
--- hint
Store everything in one `Map`. Its first key is always the least recently used, as long as you move a key to the end whenever it is used.

--- hint

=== js3-12 | Currying and composition
--- teach
**Composition** builds a function out of smaller ones by feeding each one's output into the next. Two conventions:

- `pipe(f, g, h)(x)` is `h(g(f(x)))` — reads left to right, in the order things happen.
- `compose(f, g, h)(x)` is `f(g(h(x)))` — right to left, as in mathematics.

Both are a single `reduce`:

```js
const pipe = (...fns) => (x) => fns.reduce((acc, f) => f(acc), x)
const shout = pipe((s) => s.trim(), (s) => s.toUpperCase(), (s) => `${s}!`)
shout('  hello ')   // 'HELLO!'
```

With no functions at all, both should return the input unchanged — that falls out of `reduce` naturally, as long as you pass the starting value.

Composition only works with functions that take **one** argument. **Currying** is how you get them: a curried function takes its arguments one (or a few) at a time, returning a new function until it has all of them.

```js
const add3 = (a) => (b) => (c) => a + b + c
add3(1)(2)(3)   // 6
```

A general `curry(fn)` uses `fn.length` — the number of parameters `fn` declares — to know when it has enough. Until then it returns a function that remembers the arguments so far:

- `curry(f)(1, 2, 3)`, `curry(f)(1)(2)(3)` and `curry(f)(1, 2)(3)` should all be `f(1, 2, 3)`.

Put the argument most likely to change **last** — `join(separator, list)`, not `join(list, separator)` — so that partial application gives useful single-argument pieces: `join('-')` is a function waiting for a list, ready to drop into a pipe.

One limit: `fn.length` does not count rest parameters or ones with defaults, so `curry` is for functions with a fixed number of plain parameters.
--- task
Write:

- `curry(fn)` — returns a curried version of `fn` that accepts its arguments in any grouping, and calls `fn` once it has at least `fn.length` of them.
- `compose(...fns)` — right to left; `compose()` returns its input unchanged.
- `pipe(...fns)` — left to right; `pipe()` returns its input unchanged.
- `const join` — `curry((separator, list) => list.join(separator))`.
- `const slugify` — a `pipe` that trims a string, lowercases it, splits it on runs of whitespace (`/\s+/`) and joins the words with `join('-')`.

}

}

  return function curried(...args) {
    if (args.length >= fn.length) return fn(...args)
    return (...more) => curried(...args, ...more)
  }

  return (x) => fns.reduceRight((acc, f) => f(acc), x)
}

=== js3-13 | Design: factory functions and dependency injection
--- teach
Look at code that reaches out and grabs what it needs — `Date.now()`, `Math.random()`, a global `sendEmail`, a module-level object holding state. It works, but try to *test* it: to check "a user is not emailed twice within a minute", you would have to actually wait a minute. You cannot check the message text because the id in it is random. And every caller shares one hidden state, so tests leak into each other.

**Dependency injection** is the cure: a piece of code is **given** the things it depends on instead of finding them itself. In JavaScript the lightest way to do that is a **factory function** — a function that takes the dependencies and returns an object whose methods close over them:

```js
function createGreeter({ clock = () => new Date() } = {}) {
  return {
    greet(name) {
      return clock().getHours() < 12 ? `Good morning, ${name}` : `Hello, ${name}`
    },
  }
}
const atNine = createGreeter({ clock: () => new Date(2026, 0, 1, 9) })
atNine.greet('Ada')    // 'Good morning, Ada'
```

In production you call `createGreeter()` and get the real clock by default. In a test you pass a fake clock and control time completely.

What a factory gives you:

- **Testable** code: time, randomness and the outside world become arguments you can fake.
- **Private state** in the closure, with **independent instances**: two notifiers never share a rate-limit table.
- **Explicit dependencies**: the parameter list documents everything the module touches.

Guidelines: inject what is slow, random, time-based or external (clocks, ids, network, storage); give sensible defaults so ordinary callers need not care; pass one options object, so adding a dependency later does not break existing calls; and return copies of internal state, never the live object.
--- task
The starter's `notify` is untestable: it reads `Date.now()`, makes random ids, sends through a global, and keeps its state at the top level. Replace it with a factory `createNotifier(options)`, where `options` has:

- `send(to, text)` — required; how to deliver a message.
- `clock` — returns the current time in ms; defaults to `Date.now`.
- `makeId` — returns a new id; defaults to a random string.

It returns an object with:

- `history()` — a **copy** of the list of `{ to, at }` records for every message sent, oldest first.

  const records = []

    notify(user, text) {
      const now = clock()
      if (lastSent.has(user.email) && now - lastSent.get(user.email) < minGapMs) return false

      return true
    },

      return records.map((r) => ({ ...r }))
    },
  }

=== js3-14 | Problem solving: binary search and two pointers
--- teach
When the input is **sorted**, you can answer questions about it far faster than by looking at everything. Two techniques cover a remarkable number of problems.

**Binary search.** Keep a window `[lo, hi)` that must contain the answer. Look at the middle: depending on how it compares with the target, the answer is in the left half or the right half, so throw the other half away. Each step halves the window, so a million items take about 20 steps instead of a million.

The most useful version finds the **lower bound**: the first index whose value is `>=` the target (or `length` if there is none). It answers "is it there?", "where would it go?" and "how many are smaller?" all at once.

```js
function lowerBound(a, target) {
  let lo = 0
  let hi = a.length              // the answer is somewhere in [lo, hi]
  while (lo < hi) {
    const mid = Math.floor((lo + hi) / 2)
    if (a[mid] < target) lo = mid + 1   // mid is too small: answer is to its right
    else hi = mid                       // mid might be the answer: keep it
  }
  return lo
}
lowerBound([1, 3, 3, 7], 3)   // 1
lowerBound([1, 3, 3, 7], 4)   // 3
```

Binary search is famous for **off-by-one** errors. Guard against them by writing down what `lo` and `hi` mean (here: the answer is always within `[lo, hi]`) and checking that every branch keeps that true and shrinks the window.

**Two pointers.** For "is there a pair that sums to `target`?", the brute force tries every pair — n²/2 of them. With sorted input, start one pointer at each end. If the pair sums too low, only moving the left pointer right can help; too high, move the right pointer left. Each step rules out a whole row of pairs, so one pass of n steps is enough.

The approach to any problem like this: **restate** it, work small **examples** by hand (including empty input, one item and duplicates), write the **brute force** so you have something correct, then ask *what does sortedness let me skip?*

    if (sum === target) return true
    if (sum < target) i++
    else j--
  }
  return false
}
